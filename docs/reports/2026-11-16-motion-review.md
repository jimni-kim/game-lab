# 움직이는 화면에서의 측정과 끌기 보정 검토 (2026-11-16)

범위: `motion.py`(`Steady`), `carry.py`(`Carrier`), 이 둘을 쓰는 `agent.py`·`direct.py`, 커밋 `5cf32e2`·`c987053`·`393e0f3`·`644193a`.
근거는 저장된 판 기록(`out/review/c13-*`, `d13-*`, `f13-*`), 진단 캡처 세 장, 코드, 시험, 그리고 시험의 가짜 블록 게임을 scratch에서 한 줄 바꿔 돌린 실험뿐이다. 실측과 에뮬레이터는 쓰지 않았고 저장소 코드는 고치지 않았다.

## 요약

- **"좌표 계산 방식은 맞는데 움직이는 것 때문에 잘못 잰다"는 지금 판단은 Woodoku에 대해서는 틀렸다.** `f13-woodoku`의 23번 측정은 모두 진짜 집힌 블록을 쟀다. 문제는 좌표 계산 방식이다. 이 게임은 집힌 블록을 손가락이 움직인 거리의 **약 1.43배** 움직인다. `Carrier`는 "집힌 그림 = 손가락 + 고정된 차이"로 보므로, 잰 차이가 재는 지점마다 달라지고 놓을 때 1~2칸 넘어간다. Block Game도 같은 성질(약 1.4배)로 보인다.
- `644193a`의 "손가락을 따라왔나" 확인은 이동 비율이 1이라고 가정한다. 배율이 1.43이면 거의 세로로 끄는 수에서 진짜 블록을 떨어뜨린다. Woodoku `f13`의 목표 23곳에 대입하면 **20곳이 확인에 실패한다.** `g13`에서 블록을 들고 1분 가까이 다시 집던 모습이 이것으로 설명된다(추정, `g13`은 기록이 없음).
- 합친 그림(`Steady`)은 판 읽기에는 대체로 쓸모가 있다. 끌기 측정에서는 느리고(측정 한 번에 3~5초) 트레이 쪽에 자국을 남긴다. 다만 이번 실패의 주원인은 아니다.
- 우선순위: (1) 끌기 기록을 남기고 배율을 재는 측정으로 바꿈(닫힌 고리 한 번 포함) → (2) 같은 끌기 안에서 다시 누르는 조건을 좁힘 → (3) 끌기 중에는 합친 그림 대신 원본 캡처를 쓰고 직전 그림을 다시 씀.

## 1. 지금 방식

```
                 ┌──────────── Steady.capture() (motion.still) ─────────────┐
 캡처 A ─0.25s─▶ 캡처 B ──같음──▶ B를 그대로 (moving = [])
                    └─다름─▶ 0.3s 간격으로 7장 → 픽셀별 중앙값 = 합친 그림
                                               └ 프레임과 다른 곳 = moving 상자
                                               └ 화면의 50% 넘게 움직이면 마지막 장
 ─────────────────────────────────────────────────────────────────────────────
 Carrier.carry(start, goal)                     look = animating ? Steady : snap
   before = look()            (끌기 전)
   press(start); sleep(hold)                    hold ∈ HOLDS(0, .4, .8, 1.2) — 아직 잰 적 없을 때만
   move → start + 0.2·(goal−start)              (가까우면 24px)
   sleep 0.25; during1 = look()
   candidates(before, during1)  → origin(start 옆에서 사라진 것), 모양 맞는 held 후보들
   move 32px 더 → sleep 0.25; during2 = look()
   followed: 후보 중심 이동 ≈ 손가락 이동 (±max(12px, 25%)), 크기 ±25%
   찾음 → offset = held 중심 − 손가락 (고정값으로 기억)
          end = goal − offset 로 옮기고 놓음
   못 찾음 → 0.5 구간에서 한 번 더 → 그래도 없으면 start로 돌아가 놓고 더 길게 다시 누름
```

합친 그림이 쓰이는 곳: L2 읽기(`adaptation._label`·`_frames`), 식별, 복구, `made.describe`, 직접 플레이의 질문과 `settled`(변화 판정에서 `moving` 상자 제외), `_read_code`(앞 캡처가 움직였을 때만), 그리고 위의 `Carrier.look`.

## 2. 흔들리는 원인

### 2.1 집힌 블록은 손가락의 1.4배를 움직인다: 고정 차이 모델이 틀렸다 (확신: 높음, Woodoku / 중간, Block Game)

`f13-woodoku`의 23수는 모두 `measured: true`, `tries: 1`, 처음 구간(0.2)에서 쟀다. 크기는 `origin [489,1899,114,63]` → `held 252×122~123`로 23번 모두 같다(배율 2.07~2.08). 안내 블록이나 손가락을 잰 것이라면 크기와 위치가 이렇게 일정할 수 없다.

기록된 `offset`과 `held`로 손가락 위치를 되살려(`손가락 = held 중심 − offset`) 축마다 직선을 맞추면(scratch `fit.py`):

| 축 | held 중심 − start = a + s·(손가락 − start) | 최대 잔차 |
|---|---|---|
| x | s = **1.420**, a = 26.0 | 0.56px |
| y | s = **1.448**, a = −189.5 | 0.50px |

23점이 잔차 1px 안에서 한 직선에 놓인다. 집힌 블록은 누른 순간 (26, −190)만큼 뛰어오르고, 그 뒤로 손가락 이동의 1.43배를 움직인다. "잰 차이가 끌기마다 다름(x −4~60, y −216~−296)"은 측정 오류가 아니다. 재는 지점이 목표 쪽으로 20% 간 곳이라서, 목표가 멀수록 차이가 커질 뿐이다(`offset = a + 0.43·0.2·(goal − start)`).

이 직선으로 실제 놓인 자리를 되짚으면(놓은 손가락 위치는 기록의 `end`):

- a1(튜토리얼이 요구한 빈칸, 목표 (540, 1121)): 블록 중심이 약 (536, 951)에 놓임. **y로 −170px, 칸(약 127px)으로 1.3칸 위.**
- 나머지도 목표에서 x로 −118~+112px, y로 −9~−292px 떨어진다. 목표가 트레이에서 멀수록 더 넘어간다.

23수가 모두 "효과 없음"인 것과 맞는다. PLAN §13 "두 번째 묶음"은 이것을 "안내 블록과 손가락을 집힌 블록으로 잰 것"으로 적었는데, 기록과 맞지 않는다.

Block Game(`f13-blockgame`, L2 측정 4번)은 같은 조각을 두 번 잰 a9·a10(origin `[160,1870,130,190]`)에서 손가락 x 차이 96px에 블록 x 차이 134px로 **1.40배**였다. y는 바탕이 짧아(25px) 믿기 어렵다. 다른 조각인 a8(0.5 구간에서 잼)도 1.38~1.45배로 맞는다. 점이 둘뿐이라 확신은 중간이다.

이것은 게임 하나의 성질이 아니다. 손가락이 블록을 가리지 않고, 손가락을 조금만 움직여도 판 끝까지 닿게 하려고 블록 놓기 게임들이 흔히 쓰는 방식이다. "집힌 것은 손가락 움직임의 몇 배로 움직이는가"는 화면에서 잴 수 있는 성질이다.

**재현(scratch, 저장소 변경 없음).** `tests/test_adaptation_blocks.Blocks`의 `_held_box`만 바꿔, 집힌 조각이 `start + s·(손가락 − start)`를 따르게 하고 `Carrier.carry`를 돌렸다(`gain_probe.py`).

| s | 목표 [2,2] | 목표 [0,3] | 목표 [5,0] |
|---|---|---|---|
| 1.0 | 잼, 맞게 놓음 | 잼, 맞게 놓음 | 잼, 맞게 놓음 |
| 1.2 | 잼, 맞게 놓음 | 잼, **빗나감** | 잼, 맞게 놓음 |
| 1.3 | 잼, **[1,3]에 놓음** | 잼, **빗나감** | 잼, 맞게 놓음 |
| 1.43 | **못 잼, 4번 누름**, 빗나감 4 | **못 잼, 4번 누름**, 빗나감 4 | **못 잼, 4번 누름**, 빗나감 3, **[1,0]에 놓음** |

배율이 1.2만 돼도 고정 차이 모델이 빗나가고, 1.43이면 `followed`가 진짜 조각을 떨어뜨려 다시 누르기를 다 쓴 뒤 엉뚱한 칸에 놓는다. 지금 시험의 가짜 화면은 모두 배율 1(`OFFSET` 고정)이라 이것을 잡지 못한다.

### 2.2 `followed`의 허용 폭이 배율 1을 가정한다 (확신: 높음. g13에 적용되는지는 추정)

`carry.py:50` `FOLLOW_STEP=32`, `FOLLOW_PX=12`, `FOLLOW=0.25`. 32px 움직이면 허용 폭은 max(12, 8) = 12px다. 배율 s에서 어긋남은 성분마다 32·(s−1)·|u|(u는 끌기 방향의 단위 벡터)이므로, 세로로 끌면 s ≤ 1.375까지만 통과한다. Woodoku `f13`의 목표 23곳에 맞춘 배율(1.42/1.45)을 넣으면 **20곳이 실패**한다. 통과하는 것은 대각선으로 끄는 3곳뿐이다.

실패한 뒤에는 이렇게 이어진다(`carry.py:215`, `:252`). `offset`이 None이면 `HOLDS` 네 번을 모두 쓴다. 한 번마다 before 1장 + 0.2·0.5 구간에서 각각 측정 1~2장이다. 화면이 움직이는 중이면 측정 한 장이 `Steady`의 7장 합치기라 3~5초다(`f13-woodoku`는 측정 2장짜리 한 번 끌기가 8.1~13.2초). 네 번 누르면 40~80초가 되고, **끝내 `offset`이 None으로 남아 다음 끌기도 똑같이 네 번 누른다.** 마지막에는 손가락을 목표에 놓으므로 블록은 a + 1.43·(goal − start)만큼 가서 판 위쪽으로 넘어간다. 사용자가 본 "1분 가까이 들고 여러 번 다시 집음"과 맞는다. `g13.log`가 비어 있어 기록으로 확인하지는 못했다.

### 2.3 같은 끌기 안에서 다시 누르기가 블록을 놓을 수 있다 (확신: 중간)

`393e0f3`은 못 잡으면 `move(*start)` → `lift`로 놓고 다시 누른다. 이것은 "손가락을 start로 돌리면 블록이 트레이로 돌아간다"는 가정이다. 그런데 집힌 블록은 손가락보다 위에 그려진다(Woodoku −190px, Block Game 약 −340px, `bg-hold-raw.png`). Block Game에서 트레이 y ≈ 1930이면 블록 중심은 ≈ 1590인데, 판 아래 끝이 ≈ 1608이다(`bg-tut2.png`의 1340 × 1.2). 그래서 "제자리에서 놓기"가 판 맨 아래 줄에 놓는 수가 될 수 있다. 위 scratch 실험의 s=1.43, 목표 [5,0]에서 엉뚱한 칸 [1,0]에 놓인 것이 이 경로나 마지막 놓기에서 생겼다. 조각을 탭하면 회전하는 게임에서는 내려놓았다 다시 누르는 것이 탭으로 읽힐 수 있다(손을 뗀 자리가 누른 자리와 같으므로). 1.2초 누르기가 길게 누르기 메뉴를 열 수도 있다.

### 2.4 "0.3~0.4초로는 안 집힌다"는 기록으로는 확인되지 않는다 (확신: 낮음, 반대 증거 있음)

- `f13-blockgame` a2~a4는 누름 200ms(L2 a1에서 이미 `offset`을 잰 뒤라 다시 누르기 없이 한 번)로 "확인"됐다. 본 게임에서는 0.2초로 집혔다는 뜻이다.
- `c13` a1(300ms, 끌기 1000ms, 효과 없음)과 a2(1000ms, 2000ms, 확인)는 같은 경로다. 하지만 `c13`은 다시 누르기가 없던 때라, a1은 `offset`을 못 잰 채 손가락을 목표에 두었을 수 있다(2.1의 넘어감). 누름 시간 때문인지 측정 때문인지 가릴 수 없다.
- 직접 플레이(L0)의 끌기 측정 결과(`measured`, `offset`, `tries`)는 `moves`에 남지 않는다(`agent._play_direct`의 `moves.append`에 `carried`가 없고, `direct.saw`가 모델 기록 `history`에만 넣음). 그래서 "Block Game 18번 중 4번만 잼"의 4번은 L2 4번이고, L0 14번은 기록으로 알 수 없다.

튜토리얼 단계에서만 긴 누름이 필요했을 수는 있다. 다만 지금 C5와 `HOLDS`가 근거로 삼는 관찰은 측정 실패와 섞여 있다.

### 2.5 합친 그림이 끌기 측정에 주는 영향 (확신: 중간. 이번 실패의 주원인은 아님)

- **트레이 자국.** `bg-tut2.png`에서 손가락과 안내 블록이 트레이에 오래 머물러 중앙값에 남았다(7장 중 절반 넘게 덮음). 끌기 전 그림은 이 자국이 있는 합친 그림인데, 누른 뒤에는 손가락이 사라지므로(`bg-hold-raw.png`) 끌기 중 그림은 사실상 원본이다. 그러면 자국과 조각이 한 덩어리로 "사라진 것"(origin)이 되어 origin이 커진다. `offset`은 held만으로 계산하므로 바로 틀어지지는 않는다. 하지만 배율(`scales`)이 실제보다 작게 기록된다.
- **배율 잠금.** `_plausible`(`carry.py:188`)은 받아들인 배율만 `scales`에 더한다. 처음 세 번이 튜토리얼 자국 때문에 틀린 배율이면, 그 뒤의 맞는 측정은 ±20% 밖이라 모두 버려지고 영영 바뀌지 않는다. `f13`에서는 일어나지 않았지만(Woodoku 2.07~2.08 일정, Block Game 2.5/1.89/1.82/1.84) 막을 장치가 없다.
- **시간.** `look`이 `Steady.capture`이면 끌기 전 측정만 7장(0.25 + 6×0.3초 + Android 캡처 7번, 3~5초)이다. 직전에 같은 화면을 이미 합친 그림으로 찍어 두었는데(`_play_direct`의 `before`, L2 읽기) 다시 찍는다.
- **끝점에서 멈추는 안내 애니메이션.** 튜토리얼 손가락은 보통 출발점과 도착점에서 멈칫한다. 1.8초 창의 중앙값은 그 두 곳(트레이와 목표 칸)에서 지우지 못하는데, 읽기에 가장 중요한 곳이 바로 그 두 곳이다. `f13`의 판 읽기는 빈칸을 맞게 읽었으므로(`planned_on` 3행 `[1,1,1,0,0,1,1,1]`) 판 쪽 피해는 보이지 않았다.
- **`animating` 래치.** `agent._read_code`(`agent.py:636`)는 앞 캡처가 움직였을 때만 `Steady`를 부른다. 한 번 `animating=False`가 되면 원본 캡처만 쓰므로, 나중에 생긴 반짝임이나 손가락은 다른 경로가 `seen.capture()`를 부를 때까지 알 수 없다. `Carrier`의 `look`도 끌기를 시작할 때 한 번 정해진다.

게임 하나에 맞춘 코드는 없다. 상수(`HOLDS`, `FOLLOW_PX`, `LEAST_LEG`, `FIRST_LEG`)는 Block Game 관찰에서 왔지만 게임 이름이나 모양을 아는 코드는 아니다.

## 4. 대안과 우선순위

### P1. 기록 먼저 (작음, 다음 실측 전에 반드시)

- L0 끌기의 `carried`(`measured`, `tries`, `hold_s`, `origin`, `held`, 손가락 위치)를 `moves`에 남긴다.
- `Carrier.log`에 측정마다 손가락 위치, 후보 상자, `followed`가 떨어뜨린 이유(어긋난 px), 측정 한 번의 초를 남긴다.
- 이번 검토에서 가장 큰 단서(배율)가 `offset`·`held`·`goal`이 남은 L2 기록에서만 나왔다. L0과 `g13`은 같은 질문에 답할 자료가 없었다.

### P2. 배율을 재는 측정과 닫힌 고리 한 번 (중간, 가장 큰 효과)

- 지금도 두 번 잰다(`was`, `pointer`). 두 번의 held 중심 이동을 손가락 이동으로 나눠 **배율 s**를 얻고, a = held − start − s·(손가락 − start)를 얻는다. 놓을 손가락 위치는 `end = start + (goal − start − a)/s`. s=1이면 지금과 같다.
- `followed`는 "같은 방향으로, 비율 0.7~2.0 안에서, 두 축이 같은 비율로" 움직였는지로 바꾼다. 움직이는 장식은 손가락 방향과 무관하게 움직이므로 여전히 떨어진다. 두 번째 걸음을 32px보다 길게(예: 64~96px, 아직 판 밖) 하면 s가 더 정확하다.
- **놓기 전에 한 번 더 본다.** `end`로 옮긴 뒤 원본 캡처 한 장(0.25 + 캡처 약 0.5초)으로 held 중심을 다시 재고, 남은 차이를 s로 나눠 한 번 고친 뒤 놓는다. 배율이 속도를 따르거나 판 가장자리에서 꺾이는(비선형) 게임도 여기서 잡힌다. 판 위의 그림자(놓일 자리 미리보기)가 보이는 게임이라면 그것이 목표 칸과 겹치는지가 더 직접적인 확인이다. 이것은 선택으로 둔다.
- 기억하는 것은 `offset` 하나가 아니라 (a, s)다. `HOLD`가 없는 표면에서 한 번에 끌 때도 같은 식을 쓴다.
- 장점: 화면 성질만 쓰고, 모델 질문이 0번이며, Woodoku `f13` 23수를 모두 설명하는 모델이다. 단점: 측정이 한 장 늘어난다(Android 약 0.5~1초). 배율이 시간에 따라 바뀌는 게임(easing)은 0.25초 뒤의 한 장으로 다 따라오지 않을 수 있는데, 닫힌 고리가 이것을 덮는다.
- 시험: 가짜 블록 게임에 배율(1.0·1.43·0.8)과 누른 순간 점프를 넣고 여러 방향의 목표에 맞게 놓는지 본다. scratch `gain_probe.py`가 그 틀이다.

### P3. 다시 누르기의 조건을 좁힘 (작음)

- **"안 집힘"과 "못 잼"을 가른다.** 누른 자리 근처에서 아무것도 사라지지 않았으면(origin 없음) 안 집힌 것이고, 이때만 더 길게 다시 누른다. 사라졌는데 held를 확신하지 못했으면 집힌 것이다. 다시 누르지 말고 P2의 닫힌 고리로 마친다.
- 다시 누르기 전에 "제자리에서 놓기"가 판 위에 놓지 않는지 본다. 지금 그려진 held가 판 밖인지 확인하고, 아니면 손가락을 더 아래로 옮겨 held를 트레이까지 내린 뒤 놓는다(a, s를 알면 계산할 수 있음).
- `picked_up`을 `measured`가 아니라 위의 "집힘"으로 바꾸면 C5의 최소 누름이 측정 실패로 오르지 않는다. `Direct.hold_ms`와 `Carrier.hold_s`는 하나로 합친다.

### P4. 끌기 중에는 원본 캡처, 끌기 전 그림은 다시 씀 (작음)

- 손가락을 대는 동안 안내 애니메이션이 멈추거나 사라지는 게임이 많다(`bg-hold-raw.png`). 끌기 중 측정은 원본 캡처 한 장으로 하고, 두 번 사이 차이로 held를 찾는다(두 측정의 차이에는 held의 옛 자리와 새 자리, 그리고 있다면 장식이 남는다. 같은 크기·색으로 손가락 방향을 따라 옮겨 간 짝이 held다). 끌기 전 그림(origin, 색 추리기 `_own`에 필요)은 방금 질문이나 읽기에 쓴 `Steady` 그림을 다시 쓴다. 입력이 없었으니 같은 화면이다.
- 끌기 한 번에 합친 그림 7장 측정이 없어진다(Woodoku `f13` 기준 끌기마다 3~5초 절약 추정). 트레이 자국(2.5)도 origin에 덜 섞인다. 끌기 중에도 장식이 계속 움직이는 게임은 P2의 방향·비율 확인이 거른다.

### P5. `Steady` 다듬기 (작음~중간, 읽기 쪽)

- `_plausible`의 배율 잠금을 푼다. 버린 측정도 다른 묶음으로 세어, 같은 값이 세 번 넘게 나오면 기준을 옮긴다.
- `animating` 래치: `_read_code`가 원본 캡처를 쓰는 동안에도 몇 번에 한 번(또는 상태가 흔들릴 때) `Steady`로 본다.
- 끝점에서 멈추는 애니메이션: 중앙값 대신 "가장 오래 같았던 값"을 쓰거나, 창을 넓혀도(예: 2.5~3초) 자국이 남는 곳은 `moving`으로 모델에게 알리는 것만 한다. 지금 기록에서 피해가 보이지 않으므로 마지막 순위다.

### 버린 대안

- **손가락 위치나 고정 차이를 게임마다 손으로 적기**: 방침에 어긋난다.
- **안내 애니메이션이 끝날 때까지 기다리기**: 끝나지 않는다(§13 표).
- **모델에게 끌기 중 그림을 보여 주고 차이를 묻기**: 질문과 시간이 늘어 terra 급 목표에 맞지 않는다. P2로 코드가 잴 수 있다.

## 5. 확인하지 못한 것

- **`g13-woodoku`**: 로그가 비어 있고 결과 파일이 없다. 2.2의 설명(배율 때문에 `followed`가 실패 → 네 번 다시 누르기 반복)은 코드와 `f13` 수치로 낸 추정이다.
- **Block Game의 배율**: L2 측정 두 점(같은 조각)으로 1.40배를 얻었다. L0 끌기의 측정 결과가 기록에 없어 더 확인하지 못했다. 배율이 속도에 따라 바뀌는지(빠르게 끌면 더 멀리 가는지)도 기록으로는 가릴 수 없다.
- **Woodoku 배율이 끌기 내내 일정한지**: 맞춘 점은 모두 처음 구간(목표까지 20%)이다. 판 가장자리에서 멈추거나 꺾일 수 있다. 이 때문에 P2에 닫힌 고리를 넣었다.
- **누름 시간**: 튜토리얼에서 0.25~0.4초로 정말 안 집히는지, 측정 실패가 그렇게 보였을 뿐인지(2.4). 원본 캡처로 0.2초 누르고 끄는 수동 확인 한 번이면 가려진다.
- **easing**: 집힌 블록이 손가락을 늦게 따라오는지는 기록에 0.25초 뒤의 모습만 있어 알 수 없다. Woodoku `f13`의 잔차(0.5px)를 보면 측정 시점에는 다 따라와 있었다(합친 그림 측정이라 늦게 따라온 것이 가려졌을 수는 있다).
- **"제자리 놓기"가 실제로 판에 놓는지(2.3)**: 가짜 게임에서는 생겼고, 실제 게임에서는 화면 좌표로 본 가능성뿐이다.
- **웹 블록 게임**: 이번 기록에 없다. 웹 끌기(`web.py`의 `press/move/lift`)에도 같은 `Carrier`가 쓰이므로 배율이 있는 웹 게임이면 같은 문제가 난다.
- **시험**: `.venv/bin/python -m pytest` 전체를 이 검토에서 돌렸다(결과는 아래 "시험 결과"). scratch 실험은 저장소 시험에 넣지 않았다.

### 시험 결과

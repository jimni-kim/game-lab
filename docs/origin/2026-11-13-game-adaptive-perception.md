# 게임 판독 적응 실험 계획 (규칙 모델, 풀이기, 사이트 어댑터)

작성: 2026-11-13. 브랜치: `codex/game-adaptive-perception` (`codex/game-plugin` `531f8e5c0`에서 시작). 상태: **계획 승인(2026-11-13), 구현 전.**
상위 계획: [범용 게임 플러그인 구현 계획](2026-11-09-generic-game-plugin-implementation.md), [계열 확장 계획](2026-11-12-game-family-expansion.md).
이 실험의 결과로 상위 계획 §12 전체 진행 순서 6(판 모델 재설계)을 계속할지 정한다.

## 1. 배경과 결정

**왜 하나:** 지금 구조는 계열 하나에 규칙, 풀이기, 판독(reader, controls, 프로필, 알아보기)을 묶는다. 풀이기는 등록 계열의 게임을
모델이 새로 풀 필요 없이 입증된 코드로 빠르고 강하게 두려고 둔 것이고, 그 목적은 맞았다. 그러나 사이트마다 판독이 너무 달라서
코드 수정이 대부분 판독 쪽에서 났다.

- 이 브랜치에서 game 코드를 바꾼 커밋 중 판독 쪽 파일(reader, geometry, perception, pixels, profiles, vision) 변경이 50회를 넘고, 계열 core는 8회다.
- 단계 8a 일반화는 3/6이었고, 실패한 셋은 모델에 묻기도 전에 끝났다. 판을 가리지 않는 승리 화면은 세 시도 모두 실패했다([8a 기록](../reports/2026-11-13-game-8a-eval.md)).
- 지뢰찾기 reader는 면 색이 같고 볼록 테두리로만 칸을 구별하는 클래식 클론을 읽지 못한다. 붙이며 공통 코드 세 곳을 고쳤고 걸림돌 일곱 가지가 남았다([지뢰찾기 기록](../reports/2026-11-13-game-minesweeper.md)).
- 세션 프로필(상위 §4.5)도 판독을 적응시키는 방법이지만, 정해진 프로필 칸(색상표, 테두리 색, `inset`)을 채우는 방식이라 그 칸이 표현하지 못하는 사이트에서 막혔다.
  그 칸을 넓히려던 것이 판 모델 재설계(§5.4)다.

**사용자 결정 (2026-11-13)**

| 결정 | 내용 |
|---|---|
| 판 모델 재설계 보류 | 상위 §12 전체 진행 순서 6과 §5.4 설계안을 보류. 이 실험의 성능을 보고 정함 |
| 구조 | 규칙과 입증된 풀이기는 등록해 두고, 판독은 사이트마다 실행 중에 적응(모델이 어댑터 코드를 생성) |
| 규칙 변형 | 같은 계열이라도 규칙이 다르면 "아직 못 하는 게임"으로 멈추지 않고 규칙까지 생성 |
| 판단 위치 | 생성 코드 경로는 서버가 판단(폰은 화면과 입력만). game PR 전에 다시 검토 |
| 시작 비용 | 지금은 따지지 않음(기록만). 잘 되게 하는 것이 먼저 |
| 격리 실행 | 실험(개발 PC)은 제한한 subprocess, 배포는 VM 격리(§7) |
| 기준 판독 | 손으로 쓴 reader와 등록 프로필은 실행 경로에서 쓰지 않고 회귀 비교의 기준으로만 둠 |

## 2. 목표와 범위

- **목표:** 등록 규칙 모델이 있는 게임을, 개발에 쓰지 않은 사이트에서 game 코드를 고치지 않고 판 끝까지 둔다.
  규칙이 다른 게임은 규칙을 생성해 같은 경로로 둔다.
- **대상:** 코드 풀이기로 풀리는 정적 게임(계열 확장 계획 §1). 판을 상태로 읽을 수 있고, 규칙을 "상태 + 행동 → 다음 상태"로 쓸 수 있으며,
  게임이 다음 입력을 기다린다.
- **실험 계열:** `slide_merge`(2048), `minesweeper`, `block_placement`. 규칙 변형은 Threes!류나 규칙이 다른 지뢰찾기에서 본다(§8 단계 6).

**비목표**
- 매 턴 VLM 플레이를 목표로 하는 것. 생성 코드가 실패했을 때 내려가는 바닥일 뿐이다.
- 풀이기 생성. 좋은 전략 코드는 모델이 쓰기 어렵고 맞는지 확인할 방법이 없다. 실력은 등록 풀이기(전용, 범용)에서 나온다.
- 계열 확장 계획 §5.4의 범위 밖 게임(물리, 3D, VLM 탐색형, 실시간).
- 공통 확장(레벨 범위, 대기 구간, 경로 포인터, Android). 이 실험은 판독과 규칙만 본다.
- 시작 비용 최적화, 사용자별 어댑터 기억의 운영 정책.

## 3. 구조

계열이라는 묶음을 세 부품으로 나누고, 실행 때 조합한다. `slide_merge`, `block_placement`, `minesweeper`는 규칙 모델의 id로 남는다.
계열 설명 JSON(`blueprint/families/*.json`)은 들어온 게임과 맞춰 볼 규칙 모델 목록이 된다.

```text
공통 세션 (그대로)           관측 → 추정 → 계획 → 의도 저장 → 입력 → 결과 확인
└─ 조합: FamilyModule        규칙 모델 + 고른 풀이기 + 사이트 어댑터 (지금 GridFamily 자리)
   ├─ 규칙 모델              등록 / 등록 모델의 변형(생성) / 새로 생성. 세션이 믿는 기준
   ├─ 풀이기                 등록만: 전용(지뢰찾기 확률 등) / 범용(expectimax, BFS 등)
   └─ 사이트 어댑터          사이트마다 생성: 판독, 입력 매핑, 장면, 입력 영역
      └─ 판독 도우미 라이브러리   PNG 해독, 색 샘플, 격자 찾기 (지금 pixels·geometry). 강제 스키마가 아니라 생성 코드가 가져다 씀
```

**무엇을 실행 중에 생성하나**

| 부품 | 생성 | 언제 | 사이트에 따라 다른가 |
|---|---|---|---|
| 사이트 어댑터 | 예 | 그 사이트용으로 저장된 어댑터가 없을 때 판 시작에 | 예 (유일하게 사이트마다 다름) |
| 규칙 모델 | 필요할 때만 | 규칙 변형이거나 미등록 게임일 때 | 아니요 |
| 휴리스틱 `evaluate` | 필요할 때만 | 생성한 규칙 모델에 범용 탐색을 붙일 때 | 아니요 |
| 풀이기 | 아니요 | – | 아니요 |

**지금 코드와의 대응**

| 지금 | 새 구조 |
|---|---|
| `families/<id>/core.py`의 규칙 함수 | `rules/<id>.py` 규칙 모델 |
| `core.py`의 `choose`, `POLICIES`, 탐색 내부 | `solvers/<id>.py` 풀이기(전용). 범용 풀이기는 `solvers/`에 따로 추가 |
| `reader.py`, `controls.py`, `discover.py`, `profiles/*.json` | 기준 어댑터(회귀 비교용). 실행 경로는 생성 어댑터 |
| `perception.py`, `geometry.py`, `pixels.py`, `profiles.py`, `discovery.py` | 판독 도우미 라이브러리와 어댑터 생성·채택 코드로 다시 나눔. 프로필 스키마에 묶인 부분은 줄어듦 |
| `session.py`, `execution.py`, `environments/`, `task.py`, `intake.py` | 그대로. 입력은 어댑터의 `targets`에서 준비 |

## 4. 계약

### 4.1 규칙 모델

지금 core의 규칙 함수(`validate`, `unknown_fields`, `legal_actions`, `status`, `assess`, `explain`, `ended`, `unread_state`, `initial_state`,
`next_state`, `shown`, `hidden_state`, `stray_state`, `DEFAULT_RULES`)를 그대로 쓰고, 범용 풀이기를 위해 다음을 더한다.

- `outcomes(state, action, rules) → [(가중치, 다음 상태)]`: 확정적인 게임은 하나, 무작위는 나올 수 있는 경우 전부(2048 `spawn_outcomes`의 일반화).
  나열할 수 없는 게임(지뢰찾기)은 제공하지 않는다고 선언한다.
- `evaluate(state, rules) → 정수` (선택): 탐색 휴리스틱(지금 2048·블록의 `evaluate`).
- `CAPABILITIES`: `deterministic`, `chance_enumerable`, `chance_sampled`, `constraints`, `hidden` 중 제공하는 것.

상위 §3.2의 순수 로직 조건(표준 라이브러리만, JSON 입출력, IO·시계 없음, 결정성, 공유 fixture)은 등록 규칙 모델과 풀이기에 그대로 적용한다.
생성 규칙 모델도 같은 함수 모양이어야 채택한다.

### 4.2 풀이기

- `choose(state, rules, model, budget, excluded) → 행동`. `model`은 규칙 모델(함수 집합).
- `REQUIRES`: 필요한 규칙 모델 성질(예: expectimax는 `chance_enumerable`, BFS는 `deterministic`).
- 고르는 순서: 그 규칙 모델에 등록하고 replay로 측정한 기본 풀이기 → `REQUIRES`가 맞는 범용 풀이기 → 없으면 매 턴 VLM.
- 이 실험의 범용 풀이기: expectimax(단계 3). BFS·A*, 제약 풀이, MCTS는 그것을 쓰는 계열이 생길 때 더한다.

### 4.3 사이트 어댑터

계약은 `adapters.SiteAdapter`(`framework/plugins/game/server/src/game/adapters/__init__.py`)이고, 손으로 쓴 프로필과 reader를
감싼 기준 어댑터가 `adapters/reference.py`다(단계 2). 웹 실행기는 이 호출만 쓴다.

```text
scope(measuring)            무엇을 캡처할지 (DOM 요소, 판만 자른 영역)
measure(png) / locate(png, box)   판 찾기 / 모델이 본 자리에서 다시 찾기 → 바뀌었는지
read(observation, png, dom?) → state   규칙 모델의 상태 모양 그대로(scene 포함), 못 읽은 곳은 null. 규칙 모델이 검사
target(action, state, observation, png, dom?) → 입력   같은 관측을 다시 읽어 state와 같을 때만. 키 / 탭 / 드래그 시작·끝
regions()                   게임 입력 영역(Sentinel 승인 범위는 이것들을 감싼 상자)
guarded() / picture(png)    입력 직전에 픽셀이 그대로인지 볼 영역과 그 digest
played                      조작(`kind`, `keys`)과 정착 대기
record() / restore(record)  재시작에 필요한 측정 결과
```

- `targets`는 표가 아니라 함수 `target`이다(2026-11-13 결정). 블록 배치는 (조각 × 놓을 자리)가 수백 개이고 드래그 시작점은 그 순간의
  트레이 픽셀에서 나오기 때문이다. 생성 어댑터에서도 JSON 호출이 한 번 느는 것뿐이다.
- 입력 승인 영역(`regions`)과 입력 직전 검사 영역(`guarded`)을 나눈다. DOM 사이트는 판만, 화면 판독은 판과 트레이를 검사한다.
- 장면 중 덮개와 VLM 장면 판정은 공통(웹 실행기)이다. 어댑터는 판이 보일 때의 `scene`만 낸다.
- 기준 어댑터만 쓰는 호출: `learn`(새 타일 색 배우기), `correct`(못 읽은 칸의 VLM 보정), `propose`·`adopt_profile`(프로필 없는
  사이트의 세션 프로필). 생성 어댑터는 이 자리를 재생성으로 대신하고 그대로 돌려준다.
- 어댑터는 모델이 한 번 쓰는 코드이고, 매 수 판독은 그 코드가 한다. 수마다 모델을 부르지 않는다.
- 도우미 라이브러리(PNG 해독, 색 샘플, 격자 찾기)와 DOM 글자를 쓸 수 있다. 숨은 값의 DOM 판독은 막지 않는다(계열 확장 계획 §7.2, 2026-11-13 결정).
- 어댑터는 격리된 프로세스에서 돌고 JSON만 돌려준다(§7). 판 동안 살아 있는 worker로 두어 수마다 프로세스를 띄우지 않는다.

### 4.4 저장과 재개

- 생성한 어댑터와 규칙 변형은 코드, digest, 만든 근거(관측 id, 첫 몇 수의 기록, 모델 답), 채택 시험 결과와 함께 task 상태와 artifact에 `attempt_ref`로 묶어 저장한다.
- 재시작은 저장된 어댑터로만 재개하고 다시 만들지 않는다(세션 프로필과 같은 규칙, 상위 §4.5).
- 사이트별로 저장한 어댑터를 다음 판에서 다시 쓸 수 있다. 쓸 때마다 시험 수를 다시 한다. 모든 사용자용으로 올리는 것은 검토를 거친다.

## 5. 실행 흐름

| 순서 | 하는 일 | 누가 | 실패하면 |
|---|---|---|---|
| 0 요청 | 사이트 열기. 지금과 같은 Sentinel 판정 | 지금과 같음 | 지금과 같음 |
| 1 알아보기 | 규칙 모델 목록에서 고름: 등록 그대로 / 변형 / 새 게임, 규칙 값 | 모델, 코드가 목록·규칙 값 범위 검사 | – |
| 2 첫 몇 수 | **모델은 읽고 짚기만 하고, 수는 코드가 고른다.** 모델이 판 영역 이미지(번호 격자 덧그림)와 DOM 글자로 상태 JSON과 행동의 입력 대상(칸 번호, 키)을 답함. 그 상태를 `validate`로 검사하고, 규칙 모델의 `legal_actions`와 등록 풀이기가 k수를 고름. 입력은 지금 세션 경로(의도 저장, 입력 직전 재검사, Sentinel, 영수증). 드래그 좌표와 집는 위치 보정은 계열 코드. 이 수들은 판 크기와 좌표를 실제 입력으로 확인하고 규칙이 맞는지 볼 전이 기록을 얻으려는 것이다. 규칙 모델이 없는 새 게임은 고를 풀이기가 없으므로 모델이 수를 고름 | 모델, 코드, 세션 | 읽은 상태가 검사를 못 넘으면 다시 묻고(상한 있음), 그래도 안 되면 멈춤 |
| 3 어댑터 | 사이트용 저장 어댑터가 있으면 그것, 없으면 학습용 기록을 보고 생성. 후보 여럿을 두고, 실패한 전이 하나와 그 차이를 되먹여 고침. 실행 오류는 같은 코드에서 오류만 먼저 고침 | 모델, 격리 실행 | 재생성 상한(이름 있는 상수) 안에서 반복 |
| 4 채택 시험 | ① 기록한 모든 화면이 `validate` 통과 ② **전이 하나하나를 참·거짓 시험으로**: 규칙 모델 `assess`와 일치(무작위 게임은 관측 상태가 `outcomes` 안), 통과율과 실패 전이를 저장 ③ 기록한 입력이 `targets`대로 효과를 냄 ④ 번호 격자 이미지로 VLM 교차 확인. 기록의 일부(마지막 전이들)는 생성에 보이지 않고 채택에만 씀 | 코드, 모델 1회 | ②만 실패하면 원인을 한 화면 확인으로 정하지 않음: 어댑터 재생성, 규칙 값 변경, 규칙 코드 덧붙임을 같은 기록에 돌려 **모든 전이를 설명하는 가장 작은 변경**을 채택(어댑터 → 규칙 값 → 규칙 코드 순. 잘못 읽은 것을 규칙 변경으로 맞추면 믿는 기준인 규칙 모델이 오염됨). 어느 후보도 설명하지 못하면 매 턴 VLM. 그 밖은 3으로 |
| 5 시험 수 | 풀이기가 고른 수로 상위 §4.5의 시험 수. 모두 `confirmed`여야 함 | 세션 | 3으로 돌아가거나 멈춤. 추가 입력 0 |
| 6 플레이 | 풀이기로 판 끝까지. 어긋나면 지금의 복구. 수마다의 효과 확인을 "플레이 중 전이 정확도"로 기록 | 코드 | 그 정확도가 기준 아래로 떨어지면 어댑터 재생성, 그래도 안 되면 매 턴 VLM |
| 7 저장 | §4.4 | 코드 | – |

- 모델이 다시 불리는 경우: 어댑터가 반복해서 어긋날 때, 어댑터가 모르는 장면(지금처럼 계열 `scenes`로 VLM에 물음), 매 턴 VLM으로 내려간 뒤.
- **끝 장면은 채택 시험으로 확인되지 않는다.** 승리·종료 화면은 처음 k수에 거의 나오지 않으므로 채택 통과를 끝 판정이 맞다는 근거로 쓰지 않는다. 끝은 어댑터의 `scene`만 믿지 않고 지금의 세 경로로도 판정한다: 규칙 모델의 `ended`(둘 수가 없음), 페이지 글자, 처음 보는 화면이나 효과 없는 입력 뒤의 VLM 장면 판정. 처음 보는 끝 장면을 만나면 그 화면을 기록에 더해 어댑터를 고칠 수 있다(8a의 승리 화면 실패, GIF-MCTS의 정확도와 보상 차이). 평가는 끝 판정 정확도를 따로 잰다.
- **매 턴 VLM 바닥은 한 번의 호출로 한다:** 규칙 요약(계열 설명) + 부분 상태 JSON(`null` 포함) + 번호 격자 이미지 + 합법 행동 목록 + 최근 N수 기록 → 행동 id 하나. 목록 밖 답은 한 번 다시 묻고, 또 틀리면 멈춘다. 기본 행동으로 대신하지 않고, 반성·요약용 호출을 따로 두지 않는다.
- **기록 한 줄** = (관측 id, 읽은 상태, 행동, 다음 관측, 규칙 모델의 예측과 관측의 차이). 차이는 모델이 아니라 코드가 계산하고, 어댑터 생성과 매 턴 VLM의 맥락 데이터로 쓴다.
- 첫 몇 수의 k, 재생성 상한, 다시 묻는 상한, 플레이 중 정확도 기준, 최근 N수는 이름 있는 상수로 두고 실측으로 정한다(참고: Voyager 4회, GIF-MCTS 10~50회). 모델 질문 수와 토큰은 task의 vision 예산에 포함한다.
- 근거와 출처: [게임 에이전트 조사](../reports/2026-11-13-game-agent-survey.md).
- 프롬프트(어댑터 생성, 규칙 변형 생성)는 `blueprint/prompts/`에 영어로, 게임·사이트 이름 없이 둔다. 게임 지식은 규칙 모델 설명과 등록 규칙 모델 코드를 맥락 데이터로 준다(CLAUDE.md 프롬프트 규칙, 상위 §4.2).

## 6. 안전

- **그대로 두는 것:** 상위 §6.3 안전 조건, 의도 저장 뒤 전송, 입력 직전 재검사(표면의 픽셀 대조), Sentinel 범위 제한 입력 승인, at-most-once, 영수증, 재시작 복구, 취소.
- **생성 어댑터의 출력은 믿지 않는다:** 상태는 규칙 모델이 검사하고, 좌표는 `region` 안이어야 하며 그 `region`은 Sentinel 승인 범위다. 시험 수가 확인되기 전에는 연속 진행하지 않는다.
- **생성 코드는 입력 도구, 브라우저, 키, 네트워크, 파일을 받지 않는다.** 입력은 언제나 세션이 `targets`에서 준비해 지금 경로로 보낸다. 생성 코드가 틀리면 "못 둔다"이지 "위험하게 둔다"가 아니어야 한다.
- **공정 플레이:** 경쟁·기록 모드는 하지 않는다(계열 확장 계획 §7.2).
- **가져오지 않는 것:** 모델이 쓴 코드를 입력 경로에서 실행하는 하네스(GamingAgent의 `exec`, Cradle의 기술 코드, OSWorld의 pyautogui 코드), 무효 답을 기본 행동으로 대신하는 것, 에이전트가 자기 프롬프트와 도구를 고치는 것([조사](../reports/2026-11-13-game-agent-survey.md) "제외한 것").

## 7. 격리 실행

**이유:** 생성 코드는 외부 페이지의 화면과 DOM 글자를 보고 만든 코드다. 페이지의 글이 모델을 속여 코드를 넣게 할 수 있고(프롬프트 주입),
악의가 없어도 무한 루프나 메모리 폭주가 생긴다. 서버 프로세스 안에서 돌리면 환경 변수의 키, DB의 모든 사용자 자료, 파일, 네트워크를
만질 수 있어 "에이전트는 제안만 하고 Sentinel이 결정한다"는 원칙이 깨진다. 그래서 생성 코드는 이미지와 JSON을 받고 JSON만 돌려주는
곳에서만 돌린다(상위 §10).

| 환경 | 방식 | 이유 |
|---|---|---|
| 실험 (개발 PC, macOS) | 제한한 subprocess: 환경 변수 비움, 임시 폴더만, 시간·메모리·출력 크기 제한, 가능하면 macOS sandbox로 네트워크와 파일 쓰기 차단 | `task_jail`(`vm/surface-host/src/surface_host/task_jail.py`)은 Linux 전용(namespace, seccomp). 개발자 한 사람의 PC에서 고른 사이트만 대상 |
| 배포 | VM task host의 `task_jail` | 상위 §10. 로컬 PC의 HostKit `Jail`은 경로·명령 필터뿐이라 쓰지 않음 |

- 실행기는 처음부터 "JSON만 주고받는 별도 프로세스" 계약으로 만들어, 배포 때는 실행 위치만 바꾼다.
- 배포에서 따질 점(PR 전 재검토): 판단은 서버, 격리 실행은 사람마다의 microVM이라 수마다 VM 왕복 지연이 생긴다.

각 단계는 시험과 이 문서 갱신을 포함한다. 실사이트 실행은 사이트와 규모를 정해 사용자 승인을 받은 뒤 한다. 크기는 상위 §12와 같은 기준이다.

## 10. 기존 계획과의 관계

- **보류:** 상위 §12 전체 진행 순서 6(판 모델 재설계, §5.4 설계안)과 순서 10(Rust 이식). 이식 대상인 core 계약이 단계 1에서 바뀌기 때문이다.
- **그대로:** 세션 루프와 안전 장치, task 결합, 요청 해석, 권한(코어 PR #3643), 실사이트 평가 도구, 단계 4a(Android 어댑터, 서버 판단)의 계획.
- **계열 확장 계획:** 계열 지도(§5)와 공통 확장(§6의 1·2b·3·5·6·7·8)은 그대로 쓴다. 판독 쪽 가정(E1, E3, 대부분의 E10)은 생성 어댑터가 맡는다.
  확장 4(판 모델 일반화)와 대표 계열 순서(§7.1)는 이 실험의 결과로 다시 정한다.
- **브랜치:** 이 실험은 이 브랜치에서만 한다. `codex/game-plugin`에서 공통 코드를 고치면 이 브랜치로 가져온다. 반대 방향은 결과를 보고 정한다.

## 11. 열린 결정과 PR 전 재검토

- 생성 경로를 폰 호스트에서 어떻게 할지(지금은 서버 판단, CLAUDE.md 두 호스트 규칙과의 관계).
- 배포의 격리 실행 위치와 수마다의 VM 왕복 지연(§7).
- 어댑터 생성과 규칙 변형 생성에 쓰는 모델 등급과 예산(설정 값으로 둠).
- 사이트별 저장 어댑터를 다른 사용자와 나눌지, 검토해 등록할지.
- 손으로 쓴 기준 어댑터와 등록 프로필을 결과 뒤에 남길지, 회귀 fixture만 남길지.

# game-lab 현황

2026-11-21, 세션 Z에서 정리했고, 같은 날 세션 Z2에서 실시간(§34 세션 F0~F3)을 더했다. 2026-11-23에 세 세션(R1: §32 세션 R1 기록, P2: §33 세션 P2 기록, D2: §35)의 브랜치를 main에 합친 뒤 다시 고쳤다. 코드 기준은 합친 뒤의 main이고, 합친 뒤의 수정 둘(지뢰찾기·블록 놓기의 라이브 예산 바닥 값, 데모의 판당 입력 한도)을 포함한다(PLAN §35 "합친 뒤"). 이 문서는 [PLAN.md](PLAN.md)의 세션 기록에서 숫자를 그대로 옮겼고, 새로 잰 것은 없다. 숫자마다 출처 절을 달았다(§24~§34는 PLAN, §1~§23은 [PLAN-archive.md](PLAN-archive.md)).

**읽는 법.**

- **모델.** 따로 적지 않으면 주 모델 `gpt-6.1-terra`, 경량 모델 `gpt-6-luna`이다(판마다 `summary.json`으로 확인한 기록). 세션 B·B2의 판 7개(`b1-*`, `b2-*`)는 기록에 terra로 적혔으나 실제로는 **`gpt-6.1-sol`**이다(§26 세션 C 기록의 "모델 이름 바로잡기"). sol 판은 따로 두고 terra 판과 견주지 않는다.
- **고정 / 고치며.** "고정"은 코드를 정해 두고 재는 동안 고치지 않은 판이다. "고치며"는 판 사이에 코드를 고친 묶음이라 판들을 합쳐 비율로 읽을 수 없다.
- **판 수.** 거의 모든 실측이 게임마다 1~3판이다. 비율로 적은 것은 시뮬레이션(§33)과 3매치의 레벨 연속(§26)뿐이다.
- 기록에 없는 것은 "재지 않음"이라고 적었다.

## 1. 구조

화면을 보고 웹·Android 게임을 두는 범용 에이전트다. 한 판의 흐름은 `agent.py`, 요청한 범위만큼 판을 잇는 겹은 `work.py`다. 판을 어떻게 둘지는 경로 여럿 가운데서 고른다.

| 경로 | 하는 일 | 파일 |
|---|---|---|
| 계열 키트 | 블록 놓기, 2048, 지뢰찾기, 3매치. 모델이 첫 화면을 읽어 보정하면, 그 뒤로는 코드가 판을 읽고 풀이기가 수를 고른다. 3매치의 기본 정책은 표본 탐색 `sampled`다. 라이브는 `--compute`를 계열 기술자의 바닥 값 `least_compute`까지 올린다(2048 8000, 지뢰찾기 20000, 블록 놓기 1000. §33 세션 P2, PLAN §35 "합친 뒤") | `kits/`, `adapters/kit.py`, `rules/`, `solvers/`, `blueprint/families/` |
| 다시 시작 | 등록 계열에서 모델의 판독이 "앞 판 + 수"의 결과가 아니라고 거절되면(`inconsistent`), 앞 판을 보지 않은 두 판독자(모델의 판독과 계열의 코드 판독기, 판독기가 못 읽는 칸은 경량 모델)가 칸마다 같을 때 그 화면에서 다시 시작한다. 그것도 안 되어 계열이 `inconsistent`로 판을 놓으면 직접 두기로 넘기고, 몇 입력 뒤 계열이 다시 붙는다(§32 세션 R1) | `agent._reseed`, `agent._give_up` |
| 생성 어댑터 | 모델이 판독 코드를 쓰고, 격리 실행기에서 채택 시험을 거친다. 키트가 없는 계열(클론다이크)에 남아 있다 | `adapters/generated.py`, `sandbox/`, `adaptation.py` |
| 만든 계열 | 등록되지 않은 게임을 모델이 설명하고 규칙·풀이 모듈을 쓴다(보관해 다음 판에 다시 씀). 판독기가 못 읽은 칸은 규칙이 예상한 수의 결과로 채운다 | `made.py`, `agent._teach` |
| 모델 직접 두기 | 계열이 없으면 모델이 입력을 고른다. 한 번에 12수까지 묶어 보내고, 웹은 페이지 요소를 글로 넘긴다 | `direct.py`, `environments/web.py`의 `outline` |
| 후보 중 고르기 | 3매치에서 목표를 코드가 못 재면, 풀이기의 상위 6수 가운데 하나를 모델이 번호로 고른다(§31 L3) | `solvers/match3.rank`, `agent._pick` |
| 복구 | 판을 못 찾았거나 덮개가 덮였을 때 모델이 입력 하나로 답한다 | `recovery.py` |
| 루틴 | 판 밖 화면에서 모델이 보낸 입력을 "이 화면이면 이 입력"으로 보관했다가, 같은 화면이 다시 나오면 코드가 보낸다(§28) | `routine.py`, `agent._by_routine` |
| 스토리형 | 직접 두기 위의 한 겹이다. 대사 줄은 코드가 넘기고, 선택지는 모델이 한 번 본다. 되돌릴 수 없는 선택은 방침(`--choices`)이 있을 때만 누르고, 없으면 그 자리에서 돌려준다(§27 세션 T) | `direct.py`, `agent._play_direct` |
| 실시간 | 떨어지는 블록류. 모델은 처음에 우물, 조작(키 또는 누름·쓸기), 시작 입력, 다음 조각 미리보기의 상자, 층의 목표를 한 번 말해 주고, 그 뒤로는 코드가 초당 4~8번 읽고 조작을 보낸다. 놓을 곳은 떨어지는 블록 계열(`rules/falling.py`, `solvers/falling.py`)의 풀이기가 다음 조각과 목표를 보고 고른다. 덮개·결과에서 루프가 판을 놓으면 직접 두기로 넘기고, 판이 다시 서면 루프가 다시 잡는다. 준비 답과 배운 조작은 보관한다(§29, §34) | `realtime.py`, `agent._play_realtime`, `_falling_again` |
| 세계 기억 | 요청이 바뀌어도 남는 상태(가진 것, 작업마다 다시 할 수 있게 되는 때)를 `world.json`에 둔다. 때가 안 된 작업은 남은 시간을 돌려주거나 기다린다(§30) | `world.py`, `agent._until_due` |
| 작업·범위 | 레벨 N개, 지금 화면에서 이어받기, 멈춤 조건, 허락한 판 밖 행동(`retry`, `boosters` 등)을 다루고, 끝나면 결과를 돌려준다(§25) | `work.py`, `contracts.py`, `request.py` |
| 화면 종류 | 판, 결과, 지도, 팝업, 튜토리얼, 이야기, 다른 퍼즐, 로딩. 화면을 보는 모델이 이름을 붙이고, 같은 화면을 맴도는지도 본다 | `scenes.py` |
| 화면 | 웹(Playwright Chromium), Android(ADB), 움직이는 부분 걷어내기 | `environments/`, `frames.py`, `motion.py` |
| 보관 | 사이트(앱)마다, 한 앱에 게임이 여럿이면 게임마다 폴더 하나를 둔다. 판독기, 값, 복구, 루틴, 기억(`memory.json`), 만든 계열(`made.json`), 실시간 준비 답(`falling.json`), 세계 기억(`world.json`) | `adaptation.Store` |
| 데모 페이지 | 왼쪽 게임 화면, 오른쪽 대화창. 대화창의 말(`POST /say`)을 경량 모델 질문 하나로 게임 요청·질문·중지로 가른다. 최초 요청의 답과 끝의 말은 확인된 목표와 돌려주기에서 코드가 만들고, 질문은 판과 따로 둔 대화용 모델이 마지막 화면과 코드가 센 진행으로 답한다. 루프의 진행은 `agent.progress`로 알린다(§35 세션 D2). 기기는 AVD 이름으로 고른 `game-lab`이고(세션의 실측과 같은 기기, 기기 잠금 `~/.gamelab/lock`으로 가름), 판이 돌지 않을 때 켜져 있으면 그 화면을, 꺼져 있으면 켜기 버튼(`POST /emulator`)을 보인다(§35 "데모의 기기와 켜기 버튼"). `--touch`로 켠 서버에서는 판이 돌지 않을 때 링크에서 화면을 눌러 기기를 조작한다(탭·길게 누르기·쓸기·뒤로·홈, `POST /touch`, 기본은 꺼짐, §35 "링크에서 기기 누르기") | `eval/serve.py`, `eval/serve.html`, `eval/talk.py` |

**경로를 고르는 순서.** 요청을 해석한다(`request.py`). 다음으로 식별 단계에서 실시간 게임인지(`falling`), 계열 후보가 있는지를 본다. 후보가 있으면 계열 키트나 생성 어댑터로 둔다. 후보가 없으면 설명 질문을 하고, 그 답(`fits`)이 참이면 만든 계열, 거짓이면 직접 두기로 간다. 작업 요청(`task`)은 계열을 찾지 않고 바로 직접 두기와 루틴으로 간다. 이야기 화면에서는 직접 두기 위에 스토리형 겹이 얹힌다. 등록 계열이 모델의 판독을 `inconsistent`로 거절하면 먼저 새로 읽은 판에서 다시 시작해 보고(`agent._reseed`), 그래도 판을 놓으면 직접 두기로 넘겼다가 계열이 다시 붙는다(§32 세션 R1). 다른 까닭(판이 안 보임, 입력이 안 먹음)으로 놓으면 전처럼 판이 끝난다.

**도구.** `eval web`, `eval android`, `eval offline`, `eval policies`, `eval checks`, `eval serve`, `eval models`, `pytest`. 전체 시험은 761개다. 마지막 전체 실행(752개일 때, 14.9분)에서 751개가 통과했고, 깨진 실시간 시험 하나는 따로 세 번 돌려 모두 통과했다. 그 뒤 더한 둘은 바꾼 영역과 함께 돌려 통과했다(PLAN §35 끝의 "전체 시험").

## 3. 안 되는 것과 까닭

각 세션이 "넘긴 것"·"남긴 것"으로 적고 뒤 세션이 풀지 않은 것만 모았다. 풀린 것은 §5에 있다.

### 경로 고르기

- **만든 계열의 판독기가 서지 않으면 직접 두기로 넘기는 기준이 없다.** Singles에서는 수마다 주 모델이 판을 읽어 1.4만 토큰씩 쓰다가 막혔다. 같은 퍼즐을 직접 두기로는 세 판 모두 풀었다(§26 세션 G).
- **어느 길로 갈지가 설명 질문 한 번의 답(`fits`)에 달렸다.** 같은 스도쿠 화면에서 다섯 판 가운데 한 판만 참이었다(§27 세션 S3). G가 내놓은 권고는 "갈리면 직접 두기를 먼저 하고, 만든 계열은 판독기가 첫 판을 읽을 때만"이지만, 코드에는 반영하지 않았다(§26 세션 G).
- **등록 계열이 판을 놓는 까닭 가운데 `inconsistent`만 풀었다**(§32 세션 R1). 새로 읽은 판에서 다시 시작하고, 그것도 안 되면 직접 두기로 넘겼다가 계열이 다시 붙는다. 다른 까닭(판이 안 보임, 입력이 안 먹음)으로 놓으면 전처럼 판이 끝난다. 남은 것은 이렇다.
  - 두 판독자로 다시 시작하는 길은 실측에서 0번 나왔고, 가짜 화면 시험(2048, 지뢰찾기)만 통과했다. 3매치·블록 놓기·생성 어댑터(클론다이크)에는 시험도 없다.
  - 키트와 모델이 다를 때 누가 옳은지 가리는 길이 없다. 지금은 다르면 받지 않고 직접 두기를 거쳐 돌아온다. 판은 살리지만 넘길 때마다 질문 13개·약 5.3만 토큰이 든다. 직접 두기 쪽 `RESUMES_MOST`번을 다 쓰면 그 판은 모델이 끝까지 둔다.
  - 2048 키트의 판독 정확도. 새 타일을 첫 프레임에서 받아 나타나는 중인 4를 2로 읽고(R1 1판 60/879), 굳은 256·128을 혼동한다. 틀리게 배운 표본을 다시 시작할 때 지우는 길도 없다.
  - "혼자" 길(키트가 읽은 결과가 규칙과 어긋난 뒤 키트 혼자 읽은 판에서 이어 감)은 한 판독자의 말로 간다. 다음 수에서 규칙이 다시 확인하므로 두었고, 세기만 한다(`reseeds.alone`).
- 계열 후보가 판을 놓은 뒤 만든 계열로 가는 길(Threes)은 가짜 판 시험만 통과했다(§27 S3, §26 G).

### 3매치

- **꿈의 집 10개 연속은 아직 없다.** C4는 레벨 34~38에서 5개(4개 깸)를 두다가 하트 0으로 멈췄다. 하트가 다시 차기를 기다려 잇는 길이 작업에 없다. 지금은 하트 0이면 끝내고 남은 시간을 돌려준다(§26 세션 C4). 세계 기억의 "다시 할 수 있게 되는 때"와 같은 모양의 일이다.
- **L2가 많은 레벨에서 "모델이 판을 읽은 것"을 결과에서 셀 수 없다.** 지금은 남은 PNG로 세는데, 부분마다 8장에서 잘리고 L2로 간 수는 들어가지 않는다. 판독마다 누가 읽었는지를 결과에 남기는 길이 없다(§26 세션 C4).
- **레벨의 끝을 모델의 말 하나로 판정한다.** 결과 화면 없이 지도나 팝업으로 넘어가면 그 화면에서 추정한다(`end.inferred`). 코드가 아는 목표 수는 덜 세어져 "졌다"를 뒤집지 못한다. 남은 수 칸의 숫자를 읽는 길이 없다(§25 B, §26 C3·C4). 3매치에서는 판정이 틀린 일이 없었지만, D2 실측 3(Android Block Night, 실시간)에서 처음 틀렸다. 게임이 결과 화면을 잠깐만 띄우고 레벨 목록으로 돌아가자, 목록 화면에서 모델이 "졌다"고 해 깬 레벨 둘이 진 것으로 세어졌다. 허락한 "다시 하기"는 다음 레벨을 여는 입력에 붙었다(코드는 깸 2·짐 2, 게임은 레벨 3~6을 깸. §35 D2). 레벨 번호를 앞뒤로 견주는 길도 없다.
- **판독의 세부.** 꿈의 집 판독의 28%가 상한 6.5초까지 같은 판독을 얻지 못한다. 레벨 첫 판은 여전히 모델이 읽는다. 판독기를 다시 믿는 기준(90%)은 고친 뒤 다시 재지 않았다(§26 세션 C3).
- **깬 뒤의 판 사이 길이 코드만으로 지나간 구간을 아직 못 봤다.** 레벨마다 처음 보는 창이 끼어든다(§28 D1). 같은 자리의 버튼이 다른 판을 여는 경우는 누른 자리의 모습으로만 가른다(§26 C3).
- 레벨 안에서 지는 일이 잦다(C4 레벨 38에서 4번, C 레벨 21에서 6번). 진 레벨마다 끝에서 복구 질문이 3~4개 든다. 사슬이 잔디를 막는 판에서는 "길을 여는 수"를 풀이기가 직접 재지 못한다(§31 B2).
- 수당 6~20초가 든다(판독 한 번에 3~7초, C3에서 줄지 않음). 실시간과는 거리가 멀다(§26 C3).
- sol 판에서 본 것(B, 고치지 않음): 꿈의 집 레벨 7(잔디)에서 수가 거절된 뒤 모델이 읽은 12수가 규칙과 맞지 않았다. 레벨 8(사슬)은 세 번 가운데 두 번 수가 떨어져 졌다(§25 B).
- 후보 중 고르기(L3)의 효과는 숫자가 없다. 3매치는 같은 판에서 방법을 견주지 않기 때문이다(§31, §26).
- 이름 창 알림(C2-5)은 실측에 나오지 않았고 가짜 판 시험만 통과했다(§26 d).
- 장애물 종류를 값으로 나누지 않고, 두 겹 칸과 젤리 판의 잦은 판독 의심이 남았다(§23).

### 다른 계열과 풀이기

- **라이브 기준선을 다시 잡을 계열이 늘었다.** P가 2048·클론다이크·지뢰찾기(`first_open=cell`)의 풀이기를 바꿨고(§33 세션 P), P2가 2048(라이브 예산 200 → 8000), 지뢰찾기(찍기), 블록 놓기(`search`의 끝 판 값), 3매치(기본 정책 `greedy` → `sampled`)를 바꿨다(§33 세션 P2). 합친 뒤에는 지뢰찾기(20000)·블록 놓기(1000)에도 라이브 바닥 값이 붙었다(PLAN §35 "합친 뒤"). P2와 합친 뒤의 것은 어느 것도 라이브로 재지 않았다. R1의 웹 2048 3판은 P의 풀이기, 예산 500이다.
- **클론다이크 라이브는 재지 않았다.** 기본 정책이 `hindsight`로 바뀌었고, 기억으로 맴돎을 알면 `no_progress`로 끝내게 했다. 이것은 가짜 판 시험만 통과했다. 화면을 자리로 읽는 판을 코드 생성 없이 읽는 길도 없다(수당 약 32초, §32, §11).
- 클론다이크 3장 뽑기는 계획이 greedy보다 낫지 않다(13.7% → 14.3%). P2가 run 일부 옮기기를 후보에 넣고 굴려 보기에도 넣었으나 14.1%·13.9%라 되돌렸다. 추정한 까닭(재지 않음)은 스톡 순서다: 굴려 보기 안의 수가 greedy라 어느 waste 카드를 언제 가져가 다음 바퀴의 묶음을 바꿀지 따지지 않는다. 논문과 같은 조건의 숫자도 없다(§33 P, P2).
- 지뢰찾기 30×16/99는 39.8%로 JSMinesweeper(41.0%)와 1.2%p 차이다(P2). 끝판 전부 따지기는 0이 이웃을 더 여는 것을 셈하지 않아 낮게 본다. 찍기의 수당은 30×16에서 최대 0.86초다. 라이브 게임이 첫 수에 무엇을 보장하는지 화면에서 정하는 길이 없어 기본값(`around`, 가운데부터)으로 둔다(§33 P, P2).
- 3매치 `sampled`는 수당이 2.9~7.6ms에서 56~119ms(p95 163ms, 최대 0.33초)로 늘었다. 라이브 수당의 10% 안이지만 루프의 판독과 겹쳐 잰 적은 없다(§33 P2).
- 블록 놓기의 끝 판 값은 재생 판 조각 15종으로 센다. 실제 게임의 조각 모음이 다르면 이 값도 다르다. "다음 트레이를 표본으로 뽑아 평균"은 하지 않았다(§33 P2).
- 지뢰찾기는 경량 모델이 숫자를 잘못 읽으면 규칙이 잡지 못한다. 블록 놓기는 웹 튜토리얼 구간의 비용과, 잘못 놓인 끌기에서 배우는 것이 남았다(§19, §20).

### 처음 보는 게임 (직접 두기)

- 직접 두기는 판이 긴 게임에서 비싸다. 2048은 30만 토큰으로 80~90수에서 끝났다. 묶음은 모델이 대개 한 쌍만 잡는다. 요소 글은 패가 많은 판에서 토큰을 줄이지 못했다(§27 S2, §26 G).
- Threes는 S2에서 세 번 모두 페이지가 굳었다. 까닭은 보지 않았고(보류 게임), 캔버스 게임에서 묶음의 효과는 숫자가 없다(§27 S2).
- 만든 계열은 규칙이 결과를 말하지 못하는 게임(우연히 새 조각이 나오는 것)에서 못 읽은 칸을 매번 주 모델이 읽는다. 같은 모습에 값이 다른 칸을 수가 바꾸면 경량 모델이 값을 볼 수 없다(§27 S3).
- 기준값들(요소 글 8천 자, 그림 768, 경량 모델 0.8, 못 읽은 칸 60%)은 한두 게임에서 잡은 것이다(§27 S2·S3).
- `eval`의 `model_tokens`는 실행 전체의 누적값이다. `--games` 2 이상이면 판마다의 숫자가 아니고, 판의 숫자는 `work.spent`에 있다(§26 G).
- 웹 DOM을 계열 판독에 쓰는 것(§15)과 OCR(§12)은 계획만 있다. 판당 예산 기본값(30만 토큰, 15분)은 다시 정하지 않았다(§10).

### 루틴, 이름 붙인 작업, 지속 세계

- 고친 뒤 코드만으로 재생한 판(숲 탭과 나무 모으기 둘 다 코드)은 실측에 없다. 자리의 안쪽 절반만 읽게 한 것은 마지막 실측 뒤에 고쳤다(§28 S1).
- 루틴의 일치 기준은 Android 3매치 두 게임과 웹 한 게임의 화면에서 잡은 값이다. 단계에 누른 자리의 글자(웹 DOM)를 함께 두는 일은 하지 않았다(§28 D1·S1, §27 S2).
- 작업의 끝 판정은 모델의 말에, 가진 것의 수가 그대로인지 보는 확인 하나를 더한 것뿐이다. 이 되묻기는 실측에 나오지 않았다. 닫힌 동안 수가 저절로 느는 게임에서는 틀린 끝을 못 잡는다(§28 S1).
- **다시 할 수 있게 되는 때는 모델이 화면에서 어림한 값 하나다**(덫 확인을 72초로 봤고 실제는 더 길었다). 게임을 열어 둔 동안만 흐르는 쿨다운은 `early`로 세기만 하고 쓰지 않는다. `ready_at`은 벽시계 기준이다(§30 U4, §28 S1).
- 가진 것(`have`)은 적기만 하고 고르는 데 쓰지 않는다. "할 수 있는 것 다 해줘" 같은 요청도 없다(§30 U4).
- Android 농장형 게임과 일일 보상은 재지 않았다(§30, §24 U2).
- `out/web/u2-adapters/world.json`에 틀린 기록이 남아 있다(덫 확인 횟수 2, 실제 1)(§30 U4, §28 S1).

### 실시간

- **Android는 두 게임에서 각 3판 안팎, 판마다 코드가 달랐다.** 몸짓 조작, 놓았다가 돌아오기, 끝 판정, 늦게 보이는 입력 기다리기, 쓸기 감도 배우기(두 게임 모두 "끈 거리만큼")는 섰지만 성공률은 없다. Block Night Marathon 줄 5개(F2의 끝 조건)는 재지 못했다(한도를 다 씀, §34 F2). F4에서 Tetris® 레벨 2·3을 다음 조각·목표를 쓴 채 깼지만 1판째 뒤에 고쳤고, 고친 길(다시 물은 식별의 `falling`)은 실측에 나오지 않았다.
- **떠 있는 판이 요청한 판인지 묻는 길이 없다.** "새 판"을 요청했는데 앱에 떠 있던 다른 모드의 판을 이어 뒀다(§34 F2).
- **결과 화면이 우물 위에 그려지면 마지막 조각과 그 줄을 못 센다**(Tetris® 4줄을 0으로). 그래서 결과 화면에서는 코드의 셈과 상관없이 모델의 "이김"을 받는다. 지도·메뉴에서 셈이 목표에 못 미치면 한 번 되묻지만(F3), 이 길은 가짜 게임 시험만 통과했다.
- **결과 글자가 조각처럼 읽혀** 루프가 3초쯤 몸짓을 보내다 놓는다(`piece_still`). 레벨 시작 연출에서 놓고 질문 하나를 쓴다(§34 F2).
- **다음 조각과 목표는 웹 한 게임에서만 썼다.** Android의 미리보기와 층의 목표 읽기는 실측에 없다. 미리보기가 칸 모양으로 그려지지 않거나 상자에 글자·두 번째 조각이 들면 못 읽는다. 미리보기를 쓰면서 초당 틱이 6.0 → 3.8로 줄었고 어느 몫인지는 재지 않았다(§34 F3).
- **효과가 많은 캔버스 페이지는 찍기가 느리다**(웹 teti 425ms, 초당 1.1틱). 중력이 빠른 층은 이 속도로 못 둔다(§34 F6).
- 조각 크기는 1~5칸까지(한쪽으로만 도는 것). 뒤집어 모양이 바뀌는 게임, 같은 색의 그림자 옆 1칸 조각은 다루지 않는다(§34 F6).
- 빠른 속도 구간(찍기 한 번에 두세 줄), 밀어 넣기·스핀, Hold, 대전, 다른 규칙의 게임(`clears`가 가로줄이 아니면 두지 않고 알림)은 하지 않는다(§34 범위).

### 스토리형

- **웹 한 게임(Monogatari 데모)에서 2판을 돈 뼈대다.**
- **판 밖의 다른 길은 이야기 선택지를 모른다.** 첫 식별 중의 복구(입력 3번까지)와 3매치 판 사이의 복구·루틴이 선택지를 만나면 누를 수 있다. 막은 것은 "식별 다시 묻기"와 "줄을 루틴 단계로 보관"뿐이다(§27 세션 T).
- **"되돌릴 수 없는가"는 모델의 말 하나다.** 데모의 주제 목록은 다시 돌아오는 목록인데 모델은 되돌릴 수 없다고 봤다. 틀리면 멈추는 쪽으로 틀린다. 그래서 방침 없는 요청은 선택지마다 멈출 수 있다(§27 T).
- 방침대로 고르기(`--choices`, 요청의 `choices`)와 그림뿐인 화면의 길(Ren'Py류, Android)은 가짜 화면 시험만 통과했다(§27 T).
- 2판 뒤의 고침(줄·선택지 입력을 루틴 단계로 보관하지 않음)은 다시 재지 않았다(§27 T).
- 엔딩, 저장·불러오기, 자동 넘김, 돌려준 뒤 사용자의 답을 받아 이어 가는 길은 하지 않았다. 이름 입력은 `sequence`에 글자 입력이 없어 질문 3개가 든다(§27 T).

### 데모 페이지

- **대화창은 1단계다**(§35). 도는 중에 범위 바꾸기("이번 레벨만 하고 멈춰"), 스토리 선택지에서 멈춘 뒤 사용자의 답으로 잇기, 웹 페이지를 요청 사이에 열어 두기, 에이전트가 먼저 묻고 답을 기다리기, 사용자 구분은 2단계로 넘겼다. `inferred`인 끝을 "추정"이라고 말하기, 답의 말투·길이, 여러 사람이 동시에 묻는 순서(지금은 한 번에 하나씩 답함)도 남았다(§35 D2).
- 대화는 코드의 숫자를 앞세운다. 그래서 루프가 레벨의 끝을 틀리게 세면 대화도 그대로 틀리게 말한다(실측 3, 위 "3매치"의 레벨 끝 항목).
- adb 시간 초과로 판이 한 번 끝났다(실측 2: 쓸기 한 번이 `COMMAND_TIMEOUT_S`를 넘겨 `gave_up/error`). 다시 나는지 보지 않았다(§35 D2).
- 판당 입력 한도 6000(합친 뒤)은 모든 게임에 같은 값이다. 실시간이 아닌 게임은 시간(900초)과 토큰(30만)이 먼저 걸린다. 올린 뒤 다시 재지 않았다(PLAN §35 "합친 뒤").
- 바깥에서 보는 터널은 `trycloudflare.com` 빠른 터널로 열어 왔다(사용자, 2026-11-22). 켤 때마다 주소가 바뀐다. 고정 주소(이름 붙은 터널)는 Cloudflare에 도메인이 있어야 해서 하지 않았다. 접근 토큰은 `--token`이나 `GAMELAB_DEMO_TOKEN`으로 고정할 수 있다(§35 D2).

### 정하지 않은 것

- 캔디크러쉬를 3매치 대상에 넣을지(§26 b).
- "이름·프로필을 만드는 입력"을 누르지 않는 것에 넣을지. 지금은 기본 이름으로 넘어가고 알린다(§25 B, §26 C2-5).
- 웹의 이어받기는 사이트가 스스로 저장한 진행만 잇는다. 서버가 요청 사이에 페이지를 열어 두는 길은 없다(§25 A).

## 6. 문서에서 찾은 틀린 곳 (고치지 않고 적기만)

- 세션 B·B2 기록의 "주 모델 `gpt-6.1-terra`"는 틀렸다. 실제로는 sol이다. 세션 C 기록이 바로잡았지만 B·B2의 머리 글은 그대로다.
- 커밋 `d3c3cbc`의 메시지가 일일 보상 창을 "다른 날"의 것이라고 한 것은 틀렸다(§28 D1이 이미 적음).
- §24 위쪽의 옛 세션 표에서 G 줄의 모델이 "정하지 않음"으로 남아 있다(뒤의 순서표에는 Opus 5.5로 적힘).
- README의 "전체 시험 약 3분"과 "정적 게임(…)을 두는" 소개는 낡아서, 이 세션에서 고쳤다.
- 지뢰찾기 9×9/10(첫 칸만 안전, 1만 판)의 고치기 전 숫자가 세션 P 기록에는 91.3%, 세션 P2 기록의 "옛" 열에는 91.4%다. P2는 그 사이 지뢰찾기 코드가 바뀌지 않았다고 적었다(30×16에 대해). §2 표에는 각 기록의 숫자를 그대로 옮겼다.
- 세션 D2 기록의 "실시간 게임의 입력 한도 … 정하지 않았다"는 합친 뒤 정해졌다(6000). 기록 본문은 그대로 두고 PLAN §35 "합친 뒤"에 적었다.
- 코드 주석은 따로 훑지 않았다.

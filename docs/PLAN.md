# game-lab 분리 계획

작성: 2026-11-13. 상태: **분리 완료(2026-11-13).** 실측과 실험 계획의 남은 단계는 사용자와 정한 뒤 시작.
2026-11-14: 목표를 **범용 게임 에이전트**로 넓혔다. 방침, 구조, 단계는 §10.

ARMY 게임 플러그인(`codex/game-adaptive-perception`, `92ccefe5f`)에서 게임 에이전트만 떼어 낸 독립 하네스다.
혼자 개발하며 성능을 보는 것이 목적이고, ARMY와의 결합은 나중 문제다. ARMY 저장소는 읽기만 한다.

## 1. 결정 (사용자, 2026-11-13)

- 새 저장소, 로컬에만 둔다. 원격 push 없음.
- ARMY의 안전 장치는 다시 만들지 않는다: Sentinel 승인, 입력 승인 영역, 입력 직전 픽셀 재검사, 한 번만 보내기·영수증, task 저장·lease.
- 남기는 것은 게임 로직으로서의 결과 확인이다. 수 뒤 화면을 규칙 모델의 예상 전이와 대조하고, 어긋나면 복구하거나 멈춘다.
- 웹 게임(Playwright)과 모바일 게임(ADB)을 모두 측정한다.

| 버림 | 시험 중 Sentinel·승인·task 재개·말로 한 요청(`test_game_plugin`, `test_game_intake`, `test_game_web`·`test_game_live`의 결합 시험) | 화면 환경 시험은 가짜 Surface로 새로 씀 |

**Surface 계약** (환경이 화면에 요구하는 것, 웹과 Android가 각각 구현):

```text
name, kinds                지원 입력 종류 (keys / tap / drag), reads_dom
capture(region?) → PNG     전체 화면 또는 판 영역
elements(queries) → dict   CSS 선택자로 요소의 class와 자기 글자 읽기 (웹만)
key(key) / tap(x, y, ms) / drag(x0, y0, x1, y1, ms)
```

- 키가 없는 화면(Android)에서 방향 키 조작은 판 영역 안의 스와이프로 바꾼다. 그래서 2048 프로필이 웹과 Android에서 같은 규칙·풀이기로 돈다.
- Android는 화면 판독(픽셀)만 쓴다. 프로필이 없는 게임은 지금처럼 `slide_merge`만 알아보기로 시작할 수 있다.

분리 뒤에는 실험 계획(`docs/origin/`)의 남은 단계를 이어 간다: 3 범용 풀이기 → 4 격리 실행기와 어댑터 생성·채택 → 5 지뢰찾기·블록 → 6 규칙 변형 → 7 평가.
시작은 분리 완료 보고 뒤 사용자와 정한다. 단계 4의 생성 코드는 제한한 subprocess에서 돌린다(환경 변수 비움, 임시 폴더만, 시간·메모리 제한, JSON만 주고받음).

## 5. 측정 방법

| 무엇 | 명령 | 비용 |
|---|---|---|
| 풀이기 실력 (화면 없음) | `python -m gamelab.eval policies --games N` | 없음 (CPU) |
| 세션·판독 회귀 | `pytest` (공유 fixture, 저장 캡처) | 없음 |
| 웹 실사이트 | `python -m gamelab.eval web --site NAME --games N --compute C --out DIR` | 모델 호출, 시간. **사이트와 규모를 정해 사용자 승인 뒤** |
| Android 앱 | `python -m gamelab.eval android --profile ID --package PKG --out DIR` | 같음. 에뮬레이터 `army-game`, 게임 설치는 사용자 |

- 결과: 판마다 `NAME-NN.json`(결과, 요청, 세션 기록, 수별 입력, 모델 답)과 `NAME-NN-final.png`, 실행마다 `summary.json`.
- 지표: 끝 종류와 이유, 확인된 수, 수별 효과(확인·없음·불일치), 오독(정답키가 있는 사이트), 재전송, 한 수 시간, 캡처 수, 모델 질문 수와 토큰, 페이지가 말하는 끝과의 일치.
- `--perturb`: `resize`, `cover`, `cover_bare`, `consent`, `consent_agree`, `tab`, `navigate`, `user`, `cancel`, `filter`. `disconnect`(task 재시작)는 task 저장을 뺐으므로 없다.
- 모델: OpenAI 호환 API. 기본은 Azure 앞의 LiteLLM 프록시(`https://litellm.agenticfw.dev/v1`). 키는 `AGENTIC_OPENAI_KEY`, 모델 이름은 `AGENTIC_OPENAI_MODEL` 또는 `--vision-model`(2026-11-13 사용자 결정으로 OpenRouter에서 바꿈).

## 6. 분리 결과 (2026-11-13)

- 시험 490개 통과: 옮긴 시험 441개(공유 fixture, 세션, 판독, 저장 캡처, 알아보기, VLM 질문)와 새 시험 49개(모델 클라이언트, 화면 환경, Chromium, adb, 평가 CLI).
- 원본과 달라진 동작
  - 스키마 검사가 jsonschema다. 등록 계열과 프로필은 그대로 통과한다.
  - 프로필 주소(`source.url`)가 `https://` 말고 `http://`, `android://`, `file://`도 받는다.
  - 화면 환경은 어댑터가 입력을 만들지 못하면(조각이 사라짐, 화면 밖 드롭) 그 이유로 판을 끝낸다. 원본은 이유 없이 `error`였다.
  - 동의 버튼만 있는 약관 요청은 `--accept-consent`일 때만 누른다. 게임의 계속하기 버튼은 묻지 않고 누른다.
  - 정책 평가에 지뢰찾기가 들어갔다(승률). 원본 도구는 지뢰찾기에서 오류가 났다.
- 확인하지 못한 것
  - **실사이트와 실제 모델 호출.** 웹 평가는 로컬 페이지로만 끝까지 돌렸다. 모델 API 호출은 가짜 응답으로만 시험했다.
  - **실제 Android 기기.** adb 명령은 가짜 adb로만 시험했다. 에뮬레이터 `army-game`은 켜지 않았다.
  - `--scale`(devicePixelRatio)과 `tab`·`navigate`·`filter`·`resize` 교란은 옮겼지만 돌려 보지 않았다.
- 알려진 한계
  - Android에 맞는 등록 프로필이 없다. 지금 프로필은 웹 사이트의 화면 크기와 색에 맞춰져 있다. 프로필 없이 시작할 수 있는 계열은 `slide_merge`뿐이다.
  - Android 드래그는 `input swipe`다. 길게 눌러 집는 게임(블록 배치)에 맞는지는 실기기에서 봐야 한다.
  - 웹 DOM 읽기와 캡처가 한 관측으로 묶이지 않는다(ARMY는 묶었다). 어긋나면 판독이 그 칸을 모름으로 두고 다시 본다.
  - 재시작 뒤 이어 하기(task 저장)가 없다. 세션 기록의 의도·영수증 필드는 남아 있지만 한 프로세스 안에서만 쓴다.

### 단계 4의 지금 상태

**되는 것** (시험 536개 통과, 합성 화면에서 실제 모델 `gpt-6.1-sol`로 확인: 질문 8번, 첫 생성이 채택, 60수 모두 확인)

- 흐름: 모델이 첫 6수의 화면을 읽음 → 규칙 모델이 상태와 전이를 검사, 수는 등록 풀이기 → 모델이 어댑터 코드를 씀 → 격리 실행으로 채택 시험 → 시험 수 3수 → 플레이.
- 어댑터가 못 읽는 화면에서 멈추면 그 화면 하나를 모델이 읽고 어댑터를 다시 써서 같은 판을 이어 간다(판마다 최대 16번).
- 사이트별 저장과 재사용(`out/adapters/`).

**아직 없는 것**

- 실사이트는 `march2048_4x4`, `doge2048` 각 1판만 돌렸다([기록](reports/2026-11-13-step4-web.md)). 나머지 §9 사이트와 기준선 비교는 승인받은 뒤 한다.
- 키로 두는 게임과 탭으로 두는 게임(지뢰찾기, §9)을 탐색한다. 드래그(블록)는 단계 5 후반.
- 화면만 읽는다. DOM 글자는 생성 어댑터에 주지 않는다.
- 매 턴 VLM 바닥(§5)이 없다. 어댑터를 만들지 못하면 판을 두지 않고 끝낸다.
- 규칙 불일치를 어댑터 재생성·규칙 값·규칙 코드 중 무엇으로 풀지 고르는 단계(§5-4 뒤쪽)가 없다. 지금은 어댑터 재생성만 한다.
- 채택 시험 ④(번호 격자 VLM 교차 확인)는 따로 묻지 않는다. 탐색 때 모델이 읽은 상태와의 일치로 대신한다.
- 탐색 중 덮개는 복구 경로(§8)로 넘긴다. `doge2048`이 이것 때문에 실패했고, 복구를 넣은 뒤 다시 돌리지는 않았다.
- 화면 크기가 바뀌면 생성 코드의 `measure`가 다시 재고, 못 재면 다시 배우기로 넘어간다. 돌려 보지는 않았다.

## 8. 복구 경로 설계 (2026-11-13, 사용자와 정함. 구현 순서 1~4 완료, 실측 전)

### 왜

- 지금은 코드 판독과 코드 풀이기에 지나치게 기댄다. 모델이 하는 일은 화면 읽기, 화면 4종 분류(판 / 끝·승리 / 덮개 / 모름), 어댑터 코드 쓰기뿐이고, 예상 밖 상황이 이 틀에 맞지 않으면 판이 끝난다.
- 실제 실패는 수를 잘못 두는 것이 아니라 판을 못 두는 것이다(8a 일반화 3/6, `doge2048`의 탐색 중 덮개).
- 예상 밖 상황을 코드로 종류마다 쫓아갈 수 없다. 모델 호출이 늘더라도 판이 실패로 끝나는 것보다 낫다.

### 결정

- **모델 개입 범위를 늘린다.** 코드가 막히면 판을 끝내지 않고 모델이 상황을 스스로 판단해 풀고, 판이 다시 읽히면 코드 풀이기로 돌아간다.
- **수는 계속 코드가 고른다.** 판이 읽히는 동안 모델은 수에 관여하지 않는다.
- **게임 종류와 무관하다.** 세션 공통 루프에 넣는다. 세 계열, 생성 어댑터와 등록 프로필 모두에 적용된다.
- **입력 승인 범위는 이 저장소에서 따지지 않는다.** 복구 입력은 화면 어디든 갈 수 있다. 실험 계획 §6의 Sentinel 승인 범위 제한은 ARMY와 합칠 때 정한다(§1의 결정과 같다). 지금은 게임 에이전트의 성능을 본다.

### 흐름

| 순서 | 하는 일 | 누가 |
|---|---|---|
| 1 막힘 | 세션이 판을 끝내려는 이유 가운데 화면 때문인 것: 판을 못 찾음(`board_not_found`), 못 읽음(`unreadable`), 덮개(`board_covered`), 수가 효과 없음(`absent`), 화면이 가라앉지 않음(`surface_unsettled`), 관측 시간 초과, 시험 수 실패. 탐색 중 `label_failed`도 같다 | 코드 |
| 2 묻기 | 모델에게 주는 것: 지금 화면, 막힌 이유, 마지막으로 읽힌 판 상태, 최근 N수 기록, 이 막힘에서 앞서 한 복구 입력과 그 뒤 화면이 바뀌었는지, 계열 설명(데이터) | 코드 |
| 3 답 | 상황 설명 한 줄과 다음 가운데 하나: `tap(x, y)`, `key(key)`, `swipe(x0, y0, x1, y1)`, `wait(ms)`, `give_up(reason)`. 화면 분류에 맞출 필요가 없다 | 모델 |
| 4 입력 | 답의 형식과 화면 안 좌표인지만 검사하고 보낸다. 가라앉기를 기다려 다시 본다 | 코드 |
| 5 판정 | 판이 다시 읽히면 복구 끝, 코드 풀이기로 돌아감. 끝·승리 장면으로 읽히면 그 판정대로 끝. 아니면 결과를 붙여 2로 | 코드(계열의 `estimate`) |
| 6 이어 가기 | 복구 뒤 판이 마지막 판과 같으면 그대로. 다르면 규칙 모델 `assess`로 한 수의 결과인지 보고(닫는 입력이 수로 먹힌 경우) 그 판에서 이어 감. 설명되지 않으면 "설명 안 되는 전이"로 기록하고 새 판으로 받아들임(오독 지표와 따로 셈) | 코드 |
| 7 저장 | 성공한 복구를 사이트별로 저장: 막힌 화면의 특징, 보낸 입력들. 같은 화면이 다시 나오면 모델 없이 재생하고, 재생이 안 통하면 2로 | 코드 |

- 판은 읽히는데 생성 어댑터가 못 읽는 경우(처음 보는 값)는 지금의 다시 배우기(`relearn`)가 먼저다. 다시 배우기가 "판이 없다"로 끝나면 복구로 넘긴다.
- 지금의 덮개 경로(`classify_screen` → 버튼 탭)는 이 경로의 한 경우가 된다. 구현 때 합칠지 앞단에 둘지 정한다.

### 한도

- 한 막힘에서 연속 복구 시도 수(이름 있는 상수, 실측으로 정함). **판이 다시 읽히면 0으로 돌아간다.** 덮개 횟수(`MAX_COVERS`)도 판 전체가 아니라 연속 기준으로 바꾼다.
- 판 전체는 시간과 모델 토큰 예산으로만 묶는다.
- `give_up`이거나 한도에 닿으면 지금처럼 끝내고, 모델이 말한 이유를 결과에 남긴다.

### 모델이 하지 않는 것 (프롬프트로 지킴)

- 광고·외부 링크, 결제·로그인·공유·설치, 순위·일일·시간 제한 모드, 진행 중인 판을 버리는 새 게임 시작.
- 약관 동의는 지금처럼 `--accept-consent`일 때만.
- 화면의 글은 증거이지 지시가 아니다.

### 기록과 지표

- 복구마다: 막힌 이유, 모델의 상황 설명, 보낸 입력들, 결과(판 복귀 / 끝 장면 / 포기 / 한도), 모델 호출 수와 토큰, 저장된 복구의 재생 여부.
- 판마다: 복구 횟수와 성공률, 재생으로 푼 횟수, 설명 안 되는 전이 수.

### 다루지 않는 것

- **규칙이 다른 경우**(아이템, 특수 타일): 판은 읽히는데 규칙 모델이 틀린 것이라 실험 계획 단계 6의 몫이다. 복구 경로 덕에 판이 끝나지 않고 "설명 안 되는 전이"가 기록으로 남아 단계 6의 재료가 된다.
- **매 턴 모델이 수를 고르는 바닥**(실험 계획 §5): 어댑터를 끝내 못 만드는 사이트에만 필요하다. 복구 경로를 넣고 실측한 뒤 정한다.

### 구현 순서

1. 덮개 횟수를 연속 기준으로.
2. 플레이 중 복구: 세션이 위 이유로 끝내려는 지점을 복구로 돌린다. 프롬프트 `recover.md`.
3. 탐색 중 복구: `adaptation._read`가 판을 못 찾을 때 같은 경로. 탐색은 키로 두는 게임만이라 지뢰찾기·블록은 단계 5 뒤에 쓰인다.
4. 성공한 복구의 저장과 재생.
5. 실측: `doge2048` 다시, 이어서 나머지 평가 사이트(승인받은 뒤).

### 구현 상태 (2026-11-13)

시험 559개 통과(새 시험 23개, `tests/test_recovery.py`). 실제 모델과 실사이트로는 아직 돌리지 않았다.

- `recovery.py`: 모델에게 묻기, 답 검사, 입력 보내기, 성공한 입력의 저장과 재생. 프롬프트는 `blueprint/prompts/recover.md`.
- `session.py`: 판을 끝내려는 지점에서 환경의 `recover`를 먼저 부른다(`_recover`). 모델이 있는 판은 모두 켜진다(`play`).
- `adaptation.py`: 탐색과 다시 배우기에서 판이 안 보이면 같은 경로를 쓴다. 사이트별 저장은 어댑터 폴더의 `recoveries.json`(`--generate`일 때만. 그 밖에는 한 판 안에서만 재생).
- 결과 파일: 판마다 `recoveries`(막힌 이유, 모델의 상황 설명, 입력, 화면이 바뀌었는지, 재생 여부, 판을 되살렸는지)와 요약의 `recovery`.

설계와 다르게 한 것

- **한도를 0으로 돌리는 때는 "판이 다시 읽힘"이 아니라 "수가 확인됨"이다.** 판은 읽히는데 수가 안 먹는 막힘(`absent`)에서는 판이 계속 읽히므로, 읽힘을 기준으로 하면 한도가 걸리지 않는다. 덮개 횟수(`covered_run`)도 같다. 연속 한도는 6번(`recovery.MAX_TRIES`).
- **복구 입력은 판의 행동 수(`actions_used`)에 들지 않는다.** 따로 센다(`record.recovery`).
- **같은 화면인지는 16×16 회색 축소 그림의 평균 차이로 본다**(`REPLAY_DISTANCE` 24/255). 실측으로 맞춘 값이 아니다.
- **복구 뒤 판이 달라졌는지(§흐름 6)는 따로 기록하지 않는다.** 세션이 그때 화면에서 다시 계획하므로 진행은 된다. "설명 안 되는 전이" 지표는 아직 없다.
- 모델의 답에 `none`(가리는 것이 없음. 판독 코드 쪽 문제)을 더했다. 이때는 원래대로 끝나고, 생성 어댑터는 다시 배우기로 넘어간다.
- 기존 덮개 경로(`classify_screen`)는 앞단에 그대로 두었다. 거기서 풀리지 않을 때 복구로 온다.

### 재실측 뒤 일반화 (2026-11-13)

`doge2048` 재실측 중의 수정 가운데 그 사이트에 맞춘 것을 게임과 무관하게 고쳤다.

- **복구 입력 재생:** 판이 없다는 이유로 막혔을 때만 재생한다(`REPLAYED_REASONS`). 판이 다 읽혔는데 수가 어긋난 막힘에서는 화면이 판 자체일 수 있어 재생하지 않는다. 재생한 뒤 다시 막히면 그 입력을 지운다. 같은 화면 판정은 8(추정값).
- **멈추지 않는 판:** 시험 수가 재는 대기 시간은 상태가 처음 그대로 읽힌 시점까지다. 전에는 멈추지 않음을 알아챈 시간(1초 이상)을 재서 모든 수가 1.7초씩 기다렸다.
- **다중 프레임 채택 시험:** 탐색과 다시 배우기에서 모델이 읽은 화면을 0.3초 간격으로 2장 더 찍고(모델 호출 없음, 다른 화면이 된 프레임은 버림), 생성 코드가 그 프레임들도 같은 상태로 읽어야 채택한다. 생성 프롬프트에 "프레임마다 같은 것을 근거로 읽어라"를 일반 원칙으로 넣었다.

## 9. 단계 5 전반: 지뢰찾기 (2026-11-14, 실측 전)

실험 계획 단계 5의 절반. 어댑터 생성 경로(탐색 → 생성 → 채택 → 플레이, 복구 포함)가 탭으로 두는 게임에서 돈다. 가짜 화면(계열 규칙으로 두는 9×9 지뢰찾기 그림)과 가짜 모델로만 확인했고, 실사이트와 실제 모델로는 돌리지 않았다. 시험 8개(`tests/test_adaptation_mines.py`), 전체 576개 통과.

### 한 일

- **계열 설명에 `discovery`:** `minesweeper.json`에 조작(`tap`), 화면이 보여 줄 수 있는 규칙 값(`rows`, `cols`, `mines`), 정착 대기를 넣었다. `catalog`의 검사는 "`discovery`가 있으면 알아보기 모듈도 있어야 한다"에서 "알아보기 모듈이 있으면 `discovery`가 있어야 한다"로 바꿨다. 이 블록은 탐색에도 쓰이고, 지뢰찾기는 한 번 보고 팔레트를 배울 수 없어(숫자 1~8의 잉크가 모두 보여야 함) 프로필 알아보기 모듈은 두지 않았다. 프로필 없는 지뢰찾기 플레이(`play(family_id=…)`)는 전처럼 거부된다.
- **탭 탐색(`adaptation.explore`):** 모델이 화면을 읽고 등록 풀이기가 칸을 고르면, 모델이 준 판 상자와 격자 모양으로 그 칸의 중심을 계산해 탭한다(`input_for`, `cell_box`). 보낸 입력은 생성 어댑터의 `target()`과 같은 모양(`{"kind": "tap", "x", "y"}`)으로 기록해 생성 맥락의 `examples[].sent`에 들어간다. 키 게임은 그대로.
- **전이 검사:** 바꾸지 않았다. 지뢰찾기 규칙 모델의 `assess`가 이미 "연 칸이 숫자이고, 0에서 이어 열린 칸 말고는 바뀐 것이 없다 / 지뢰를 열어 끝났다"를 참·거짓으로 판정하므로 그대로 `confirmed`를 요구한다. 숨은 값이 드러나는 게임이라 `outcomes`가 없고 필요하지도 않다. 2048의 검사도 그대로다.
- **탐색 중 게임 끝:** 첫 수는 추측이라 지뢰를 열 수 있다. 끝난 판(`legal_actions`가 빔)에서는 탐색을 멈추고, 그 화면도 하나의 look으로 둔다(지뢰가 터진 모습은 어댑터가 읽어야 하는 값이다). 기록이 충분하면(look 5개 이상) 어댑터를 만들고, 플레이는 그 화면을 읽어 `game_over`로 끝난다(어댑터는 사이트별로 저장돼 다음 판에 쓰임). 부족하면 `AdaptationFailed("game_ended", "N moves were played before the game ended")`. 새 게임은 시작하지 않는다: 어느 버튼이 새 게임인지 모르고, 복구 프롬프트의 원칙(진행 중인 판을 버리는 새 게임 금지)과도 어긋난다.
- **탭 채택 허용 범위(`adopt`):** 키는 전처럼 같은 키여야 한다. 탭은 어댑터가 재어 낸 판 상자에서 그 수가 가리키는 칸의 상자 안에 들어오면 통과한다(`_same_input`). 하네스가 탭한 픽셀은 모델의 대략적인 상자로 계산한 것이라 픽셀 일치는 지나치게 엄격하고, 같은 칸 안의 다른 점은 같은 수다. 옆 칸, 판 밖, 키로 답하면 `target` 실패로 돌려 준다.
- **프롬프트:** `generate_adapter.md`에 탭의 `target()` 모양(자기 `measure()`가 찾은 판 상자로 계산한 칸의 중심)과 `examples[].sent`의 설명을 더했다. `label_screen.md`의 규칙 값 설명을 "판 크기와, 계열이 나열하면 화면이 판 옆에 보여 주는 개수"로 넓혔다(지뢰 수). 게임·사이트 이름은 없다.
- **(2026-11-14 뺌, §10 G1) 탭 게임의 복구 안전(`recovery.py`, `screen.py`):** 계열의 행동 입력이 `tap`이면(`Recovery.taps_cells`) 모델이 답한 탭이 칸 상자(`avoid`) 안에 떨어질 때 거부하고(`log[].refused`), 저장된 복구 입력도 칸 위면 재생하지 않는다. 칸 상자는 탐색 중에는 모델이 준 판 상자, 플레이 중에는 어댑터가 재어 둔 영역(`regions()`)이다. 키 게임은 영향이 없다(덮개 카드를 판 위 탭으로 닫는 `doge2048`의 복구는 그대로). `recover.md`에 같은 원칙을 한 문장 더했다.

### 계획과 다른 것, 아직 없는 것

- **복구 탭은 칸을 피하지 않는다(§10 G1).** 코드 쪽 거부는 뺐고, 칸에 닿는 탭이 수가 된다는 것은 `recover.md`가 모델에게 알린다. 문제가 생기면 그때 다시 넣는다.
- **(2026-11-14 고침, §10 G2) 지뢰 수는 모르는 채로 둔다.** 탐색의 모든 화면에서 모델이 같은 숫자를 읽었을 때만 그 숫자를 쓰고, 아니면 null이다. 전에는 못 읽으면 표준값 10을 썼다.
- **끝난 판 뒤 새 게임을 시작하는 길이 없다.** 탐색 중 지뢰가 터지면 그 판은 끝이고 다음 판을 다시 돌려야 한다.
- **실사이트 실측은 §10 G4에서 했다**([G4 실측 기록](reports/2026-11-14-g4-minesweeper.md)).
- **블록 배치(드래그, 집는 위치 보정)는 단계 5 후반.** `EXPLORED_WITH`에 `drag`는 없다.
- 가짜 지뢰찾기 화면의 첫 수는 replay 게임의 보장(첫 칸 주변에 지뢰 없음)을 따른다. 보장이 다른 사이트(첫 칸만 안전, 보장 없음)에서는 첫 수 뒤 끝나는 비율이 다르다.

## 10. 범용 게임 에이전트로의 전환 (2026-11-14, 사용자 방침. 계획만, 코드 변경 전)

### 방침

- 이 저장소는 ARMY와 무관한 개인 저장소다. 목표는 **웹·모바일 게임을 두는 범용 에이전트**다. ARMY에 붙이는 것은 맨 나중 일이다.
- ARMY 운영 방식(사이트마다 사람이 프로필 등록, 사람의 입력 승인, task 저장·재시작 복구)은 설계 제약이 아니라 걷어낼 대상이다.
- 처음부터 다시 시작하지 않는다. 남기는 것: 규칙 모델과 풀이기, 생성 어댑터 경로(탐색 → 생성 → 채택 → 다시 배우기), 격리 실행기, 복구 경로, 실측 도구와 기록. 세션 루프(`session.py`)는 새로 쓴다.
- 막히면 판을 끝내기보다 모델이 풀게 한다. 게임·사이트 전용 처리보다 공통으로 통하는 방식을 택한다.
- 첫 범위는 턴제·이산 상태 게임이다. 실시간 게임(러너, 슈팅, 물리)은 "보고 → 한 수 → 확인" 루프 밖이라 뒤에 따로 설계한다.

### 구조 판단

지금 구조("모델이 판독 코드를 쓰고 코드 풀이기가 수를 고름")는 턴제·이산 게임에 맞다. 근거는 2048 평가 사이트를 사이트 전용 코드 없이 2048까지, 수당 0.65초, 정답키가 있는 곳의 오독 0으로 둔 것이다([단계 4 실측 기록](reports/2026-11-13-step4-web.md)). 범용으로는 네 가지가 빠졌다.

| 빠진 것 | 지금 | 바꿀 방향 |
|---|---|---|
| 바탕이 거꾸로 | 코드 경로가 바탕, 모델은 막힐 때만. 규칙 모델 없는 게임은 시작 못 함(`catalog.py`, `play.py`의 `family_not_discoverable`) | 모델 루프가 바탕. 코드로 대신할 수 있게 되면 빠른 경로로 올라감 |
| 게임 이해 단계 없음 | 사람이 `--site`와 계열을 지정 | 등록 계열인지 모델이 고르고 첫 전이로 확인 → 비슷하면 규칙 변형 → 처음 보는 게임이면 모델이 직접 |
| 상태 = 행×열 격자 | `label_screen.md`, `overlay`, `_shape`, `cells`, `cell_box`, 채택 시험의 탭 비교 | 상태는 스키마가 있는 JSON, 입력 대상은 이름 있는 요소와 그 상자 |
| 실시간 게임 | 구조 밖 | 범위 밖으로 둠. 따로 설계 |

**단서 (검토에서 더한 것)**

- **"모델이 바탕"은 제어 구조의 뜻이지, 모델이 수를 고르는 것이 기본이라는 뜻이 아니다.** [조사](origin/2026-11-13-game-agent-survey.md)의 결과는 모델 직접 플레이가 가장 약한 고리라는 것이다(VideoGameBench 0.48%, 드래그 0~10%, CWM for GGP의 LLM 직접 플레이는 위법 수로 기권). 성능은 빠른 경로에서 나온다. 규칙을 아는 동안 수는 언제나 코드가 고른다.
- **비용이 경계를 정한다.** 2048 한 판은 약 1,000수다. 모델이 매 수를 읽으면 질문 1,000번이고, 생성 어댑터는 4.6만 토큰으로 끝났다. 긴 게임은 빠른 경로 없이는 예산 안에 못 둔다.
- **규칙 없는 게임의 결과 확인이 없다.** 지금 모든 확인은 규칙 모델의 `assess`다. 바탕 루프에서는 더 약한 공통 확인이 필요하다: 모델이 입력과 함께 "무엇이 바뀔지"를 말하고, 코드가 앞뒤 화면의 차이로 바뀌었는지만 본다(조사의 "코드가 만든 차이 한 줄").
- **처음 보는 게임의 규칙 코드 생성은 근거가 가장 약하다.** 공개된 성공 사례는 모두 상태를 기호로 받았다(조사). 화면에서는 상태 스키마, 판독, 규칙을 한꺼번에 정해야 한다. 맨 뒤에 두고, 없어도 바탕 루프로 둘 수 있게 한다.
- **격자 일반화는 대상 게임 하나를 정해서 한다.** 대상 없이 넓히면 맞는지 확인할 방법이 없다.
- **보류 세트가 필요하다.** 세 계열에서만 재면 범용이라는 말을 할 수 없다. 개발 중 보지 않는 게임 목록을 따로 둔다.
- **세션은 처음부터 새로 쓰고, 기존 세션은 보관한다(사용자 결정).** `session.py` 661줄과 시험 816줄에는 실사이트에서 배운 것(광고가 다시 뜨는 페이지, 멈추지 않는 판, 보내기 전 거부된 입력)이 있다. 그대로 두어 기준선 경로가 계속 쓰게 하고, 새 루프에서 같은 문제가 나오면 거기서 가져오거나 보강한다. 검토 의견은 처음에 "지금 세션 위에 얹고 나서 덜어내기"였으나 다시 보고 새로 쓰기에 동의했다(아래 "새 루프를 새로 쓰는 근거").

### 계층과 경계

| 단계 | 누가 읽나 | 누가 수를 고르나 | 필요한 것 | 수당 비용 |
|---|---|---|---|---|
| L0 모델 조작 | 모델 | 모델(입력 하나) | 없음. 메뉴, 튜토리얼, 덮개, 처음 보는 게임 | 질문 1 |
| L1 모델이 읽고 목록에서 고름 | 모델 | 모델(규칙 모델의 합법 행동 id 하나) | 규칙 모델, 풀이기 없음 | 질문 1 |
| L2 모델이 읽고 코드가 고름 | 모델 | 풀이기 | 규칙 모델, 풀이기 (지금의 탐색) | 질문 1 |
| L3 코드가 읽고 코드가 고름 | 생성 어댑터 | 풀이기 | 채택된 어댑터 (지금의 플레이) | 0 |

- **올라가는 조건은 증거다. 모델의 말이 아니다.**
  - L0 → L2: 모델이 고른 계열로 읽은 상태가 `validate`를 통과하고, 첫 k수의 전이가 모두 `assess`로 확인됨. 계열 식별이 틀리면 여기서 걸린다.
  - L2 → L3: 채택 시험 통과, 이어서 시험 수 확인(지금 그대로).
- **내려가는 조건**
  - L3 → L2: 어댑터가 못 읽거나 잘못 읽음. 먼저 다시 배우기(한 화면). 다시 배우기가 연속으로 실패하거나 어댑터를 못 만들면 **판을 끝내지 않고 L2로 그 판을 이어 간다**(실험 계획 §5의 "매 턴 VLM 바닥").
  - L2·L3 → L0: 판이 화면에 없음(덮개, 메뉴, 끝 화면). 지금의 복구가 이것이다. 판이 다시 읽히면 돌아온다.
  - 규칙 밖: 모델과 코드의 판독은 일치하는데 전이가 계속 규칙과 어긋남. 규칙 변형이 있으면 그것으로, 없으면 L0(상태 표를 함께 줌)로 두고 "규칙 밖"으로 기록한다.
- **오르내림을 막는 것:** 내려온 뒤에는 수가 m번 확인돼야 다시 올라간다. 한 판에서 두 번 실패한 단계는 그 판에서 다시 시도하지 않는다. 값은 이름 있는 상수로 두고 실측으로 정한다.
- **한도:** 판 전체는 시간과 모델 토큰 예산으로만 묶는다. 남은 예산으로 지금 단계를 이어 갈 수 없으면 예산 사유로 끝낸다.
- **조사와의 관계:** 어긋나지 않는다. 조사의 제안(모델은 읽기와 위치 짚기, 고르기는 코드, 답은 목록의 id, 무효 답에 기본 행동 없음, 모델 코드를 입력 경로에서 실행하지 않음)을 그대로 따른다. 자기 프롬프트를 고치는 방식(Continual Harness)은 계속 쓰지 않는다.

### 새 루프를 새로 쓰는 근거와 통과 기준

- **루프가 이미 세 개다.** 탐색(`adaptation.explore`)은 모델이 읽고 풀이기가 고르는 루프를 세션 밖에서 돌린다. `play_adaptive`는 세션을 감싸 다시 배우기를 돌리고, 복구는 양쪽에서 불린다. 위에 얹으면 네 번째 층이 된다.
- **L0~L3은 한 루프의 설정 차이다.** "누가 읽고 누가 고르나"만 다르다. 읽는 쪽과 고르는 쪽을 갈아 끼우는 루프 하나가 지금 세 군데에 흩어진 것보다 작다.
- **"덜어내기"가 사실상 제약 붙은 재작성이다.** 의도 저장·영수증·epoch 타입이 세션, 환경, 어댑터, replay에 걸쳐 있고, `test_session.py`의 상당수가 그 장치를 시험한다.
- **매치3이 요구하는 것을 지금 세션이 막는다.** 한 수가 입력 여러 개인 교환, 연쇄가 끝난 뒤의 확인(`session.py:585, 587`).
- **위험은 `session.py`보다 `screen.py`(564줄)에 있다.** 판 재기, 정착 대기, 덮개 판정이 거기 있고 생성 경로도 이것을 거친다. 새 루프는 탐색처럼 `Surface`와 생성 어댑터에 직접 붙고, `screen.py`에서는 정착 대기만 가져온다.
- **지킬 동작은 코드가 아니라 시험으로 옮긴다:** 멈추지 않는 판, 효과 없는 수의 제외, 보내기 전 거부된 입력, 채택 뒤 시험 수, 화면 크기 변경, 끝 판정.
- **통과 기준:** `play_adaptive`를 거치는 가짜 화면 시험(`test_adaptation.py`, `test_adaptation_mines.py`, `test_recovery.py`)이 새 루프로 통과한다. `test_session.py`는 기존 세션과 함께 기준선에 남긴다. 마지막으로 2048 사이트를 다시 실측해 수당 0.65초와 오독 0이 유지되는지 본다(사용자 승인 뒤).

### 게임 식별 경로 (G3)

지금은 계열을 사람이 정한다: `eval web`은 `sites.json`의 `family`나 `--profile`에서 받고, `discover_screen.md`는 주어진 계열이 맞는지만 답하며, `setup_game.md`는 부르는 코드가 없다.

| 순서 | 하는 일 | 누가 |
|---|---|---|
| 1 들어가기 | 주소나 앱을 열고 시작 화면·동의·메뉴를 지나 판이 보이는 데까지 감 | 모델(지금의 복구와 같은 방식) |
| 2 후보 고르기 | 화면과 등록 계열 설명서 전부를 주고, 맞는 계열을 순서대로 고르거나 "없음"이라고 답하게 함. 요청의 말과 화면의 게임 이름은 힌트 | 모델, 질문 1번 |
| 3 상태로 확인 | 첫 후보의 설명서로 화면을 읽고 그 규칙 모델의 `validate`를 통과하는지 봄 | 코드 |
| 4 전이로 확인 | 풀이기가 고른 수를 몇 번 두고 매번 `assess`로 확인 | 코드 |
| 5 판정 | 모두 확인되면 그 계열로 둠. 상태부터 안 맞으면 다음 후보. 상태는 맞는데 전이 일부가 어긋나면 비슷한 게임(규칙 변형 G10, 그 전에는 모델이 직접). 후보가 없으면 처음 보는 게임(L0) | 코드 |
| 6 기억 | 사이트별로 계열과 규칙 값을 저장해 다음에는 2~4를 건너뜀 | 코드 |

- 3~4는 지금의 탐색이 하는 일이다. 빠진 것은 2의 질문, 후보를 차례로 시도하는 반복, 실패했을 때의 갈래다.
- 규칙 값도 이 경로에서 정해진다. 판 크기는 3에서 읽고 4에서 확인되고, 확인할 수 없는 값은 모르는 채로 둔다(규칙 값 원칙).
- 모델의 답은 후보일 뿐이다. 전이가 안 맞으면 채택하지 않는다.
- 한계: 확인하려면 수를 둬야 한다(지뢰찾기는 첫 수가 추측). "틀린 계열", "비슷한 변형", "판독 실수"를 가르는 기준(확인된 전이의 비율)은 실측으로 정한다.

### 규칙 값 원칙 (세 계열 공통)

1. **최대값을 두지 않는다.** 최소값은 근거가 있을 때만 둔다(2048 알아보기의 3은 `geometry.frame`의 조건).
2. **모르는 값은 모르는 채로 둔다(null).** 규칙 모델과 풀이기는 그 값 없이 돌아야 한다. 약해질 수는 있어도 틀린 추론을 하지 않는다.
3. **틀린 값은 모르는 값보다 나쁘다.** 화면에서 읽은 값은 전이로 확인될 때만 쓴다.
4. **플레이 중 값이 화면과 어긋나면 그 값을 버리고 계속 둔다.** 판을 끝내지 않는다.
5. **값을 아는 경우의 같은 seed 리플레이 성적은 바뀌지 않아야 한다.** 바꾸기 전에 수순을 기록해 비교한다.

**위험 1: 지뢰 수를 모를 때 (고친다)**

- 지금: 모델이 못 읽으면 기본값 10(`families/__init__.py:72`). 쓰이는 곳은 `rules/minesweeper.py:50`(`_won` → `legal_actions`, `status`, `assess`), `:74`, `solvers/minesweeper.py:50, 73-77, 163-186`.
- 규칙: `mines`가 null일 수 있다(`rule_parameters.mines.values`의 type에 null). `DEFAULT_RULES`는 10 그대로(replay와 등록 프로필).
- 승리 판정: (수를 알고, 열린 칸 수가 맞고, 모든 숫자가 주변의 안 열린 칸 수와 같음) 또는 (덮인 칸이 없음) 또는 (안 열린 칸마다 그런 숫자 이웃이 있음 = 지뢰로 증명됨).
- 풀이기: null이면 전체 수 추론을 건너뛰고, 확률은 칸마다 독립 밀도(시제품 1/6)로 계산한다. 수를 써서 둘 칸이 없는데 규칙상 판이 안 끝났으면 그 수만 수 없이 푼다(규칙 값은 바꾸지 않음. 세션·어댑터·리플레이 변경 없음). 규칙상 이미 이긴 판에서는 이 길을 타지 않는다.
- 탐색: 화면이 알려 주지 않고 스키마가 null을 받는 규칙 값은 null로 둔다(`adaptation._rules`, 게임 이름 없는 공통 규칙).
- **화면 카운터(사용자 결정): 기본은 null이고, 탐색의 모든 화면에서 모델이 같은 숫자를 읽었을 때만 그 숫자를 쓴다.** 추가 질문은 없다(판독 답에 이미 규칙 값이 있다). 화면마다 바뀌는 숫자(타이머)는 여기서 걸러진다. 채택한 숫자가 틀려도 위의 "수 없이 풀기"가 받는다. 검토 의견은 "읽지 않음"이었다: 읽어서 얻는 것이 0~3%p다.
- 남는 위험: 열린 이웃이 없는 지뢰 칸은 숫자로 증명되지 않는다(16×16에서 1%). 사이트가 깃발을 자동 표시하지 않으면 그 판은 판정 없이 끝난다(`screen.py`의 `_judge_stalled`가 버튼 없는 승리 장면 답을 버림). 실측에서 보고 정한다.
- 시험: 공유 fixture에 null 경우, 변경 전 수순과의 비교, 틀린 수로도 판이 끝까지 가는지, `eval policies`에 지뢰 수를 숨긴 변형.

**위험 2: 판 크기 상한 (없앤다)**

- 상한이 지키는 것은 없다. 규칙 모델·풀이기·리플레이에 크기에 묶인 코드가 없고, 풀이기 시간은 결정당 평균 16×30에서 3ms, 50×50에서 43ms, 80×80에서 114ms다. 지금 상한은 16×30 판을 `rules_refused`로 막기만 한다.

- 큰 판에서 모델의 판독 정확도는 재 보지 않았다.

**위험 3: 복구 탭의 칸 회피 (사용자 결정: 뺀다. 문제가 생기면 그때 넣는다)**

### G2 구현 기록 (2026-11-14)

- **지뢰 수 null:** 규칙 모델(`_won`, `validate`, `status`), 풀이기(`_deduce`, `_odds_uncounted`, `choose`의 수 없이 다시 풀기), 계열 설명서(`mines`가 null을 받음). replay 게임은 지뢰를 놓아야 하므로 null이면 `mines_unknown`으로 거부한다.
- **탐색:** null을 받는 규칙 값은 모르는 채로 첫 수들을 두고, 탐색의 모든 화면이 같은 값을 말했을 때만 그 값을 기록에 넣는다(`adaptation._rules`, `_told`). 계열 이름은 코드에 없다.
- **상한:** 세 계열 설명서의 판 크기 최대값과 지뢰 수 255를 뺐다. 확대 그림은 칸이 56px보다 작아지지 않게 커지고(긴 변 2400px까지), 판독 답 한도는 16000토큰이다. 생성 맥락의 `cells()` 크기는 그대로다.
- **확인:** 바꾸기 전에 기록한 78판(세 크기, 두 정책, `tests/fixtures/game/minesweeper_games.json`)이 칸 하나까지 같다. 공유 fixture에 null 경우 14개. 틀린 수(8, 12)로도 40판이 멈추지 않는다.
- **재현:** `python -m gamelab.eval policies --family minesweeper --games 200 --hide mines` → 지뢰 수를 알 때 승률 0.96, 숨기면 0.97(같은 seed, 더 나음 2, 같음 198, 못함 0).
- **남은 것:** 2048의 `spawn`·`target`, 블록의 `tray_size`를 모르는 채로 두는 것. 지금까지 실측한 2048 사이트는 모두 표준값으로 통과했으므로, 어긋나는 사이트가 나올 때 한다.

### G3 구현 기록 (2026-11-14)

- `play_adaptive(surface, model, None, ...)`: 계열을 주지 않으면 화면에서 알아낸다(`adaptation._begin`, `identify`). 평가 CLI는 `eval web --generate --identify`.
- 질문 하나(`prompts/identify_game.md`): 화면과 탐색할 수 있는 계열(지금은 `minesweeper`, `slide_merge`)의 설명을 주고 후보를 순서대로 받는다. 최대 3개.
- 후보마다: 그 계열로 화면을 한 번 읽어 규칙 모델이 받는지 본다(`Adaptation.probe`, 수를 두지 않음). 받으면 그 읽기에서 탐색을 시작하고, 첫 수들의 전이가 어긋나면 다음 후보로 간다.
- 판이 안 보이는 첫 화면(시작 화면, 알림)은 복구 경로로 지난다. 이때 모델에게 계열은 null, 이유는 `game_not_shown`이다.
- 사이트에 저장된 어댑터가 있으면 질문 없이 그 계열로 시작한다.
- 맞는 계열이 없으면 `unsupported / game_not_identified`로 끝난다. 모델이 직접 두는 길(L0)은 G5.
- 시험 7개(`tests/test_identify.py`). 아직 없는 것: 읽기는 통과했는데 전이가 어긋나는 "비슷한 게임"의 가짜 화면 시험.

### 단계

단계마다 바꾼 영역의 시험만 돌리고 커밋한다. 실사이트 실행과 실제 모델 호출은 사이트와 규모를 정해 사용자 승인 뒤에 한다. 사용자 결정과 재검토에 따라 처음 적은 순서를 고쳤다(게임 식별을 G3으로 넣고 뒤를 한 칸씩 밀었다).

| # | 단계 | 완료 조건 | 크기 | 실측 |
|---|---|---|---|---|
| G1 (완료) | 위험 3 제거 | 칸 회피 코드와 거부 시험이 없음. `recover.md`가 사실과 맞음 | S | – |
| G2 (지뢰찾기와 상한 완료, 2048·블록 값 남음) | 규칙 값 원칙 | 지뢰 수 null과 "모든 화면에서 같으면 채택"(위험 1), 상한 제거와 확대 그림·토큰 비례(위험 2), 2048의 `spawn`·`target`과 블록의 `tray_size`를 모르는 채로 둠. 값을 아는 경우 같은 seed 수순이 그대로. `eval policies`에 값을 숨긴 변형 | M | 오프라인만 |

- G1 → G2 → G3 → G4는 지금 구조 안의 수정과 추가라 먼저 한다. G5부터가 전환이다.

### 열린 결정

- 대상 게임 묶음(위 권고)을 그대로 쓸지.
- 캔디크러시사가의 실행 경로와 약관 확인 결과에 따라 실측을 어디서 할지.
- 매치3의 공개 웹 클론으로 어느 사이트를 쓸지(G8 착수 때).
- 판당 예산 기본값(입력 30만 토큰, 15분)은 G4·G5 실측 뒤 다시 정함.

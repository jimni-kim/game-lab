# game-lab 계획

2026-11-17에 다시 썼다. 그 전의 계획과 실측 기록(§1~§23, 2053줄)은 [PLAN-archive.md](PLAN-archive.md)에 그대로 있다.

**절 번호.** 코드와 시험의 주석이 가리키는 `PLAN §1`~`§23`(과 소문자 `plan §N`)은 보관 파일의 절이다. 이 파일의 번호 붙은 절은 §24부터다.

## 목적

화면을 보고 웹·Android 게임을 두는 범용 에이전트다. 개인 연구이고 ARMY와의 결합은 맨 나중 일이다.

2026-11-17에 목적을 넓혔다. **한 판을 깨는 것이 아니라, 사용자가 맡긴 범위를 끝내고 돌려주는 것이다.**

- **성능.** 사용자가 깨기 어려운 판을 혼자 깰 수 있다는 것을 숫자로 보인다.
- **범위.** 하던 판을 이어받기, 한 판만, 여러 판 연속, 조건이 되면 멈추기를 요청대로 한다.
- **게임 종류.** 아케이드류(블록 놓기, 3매치, 2048, 지뢰찾기)에 한정하지 않는다. 농장형 게임에서 아이템을 얻는 반복만 맡기거나 수확만 맡기는 것, 스토리형, 테트리스 같은 실시간 게임까지 넓힌다.

| 계열 키트 | 블록 놓기, 2048, 지뢰찾기, 3매치. 모델의 첫 화면으로 보정한 뒤 코드가 읽고 풀이기가 고름 | `kits/`, `adapters/kit.py`, `rules/`, `solvers/` |
| 생성 어댑터 | 모델이 판독 코드를 쓰고 격리 실행기에서 채택 시험. 키트 없는 계열(클론다이크)에 남음 | `adapters/generated.py`, `sandbox/`, `adaptation.py` |
| 만든 계열 | 등록 안 된 게임을 모델이 설명하고 규칙·풀이 모듈을 씀. 그 판 동안만 | `made.py` |
| 모델 직접 두기 | 계열이 없으면 모델이 수마다 입력 하나를 고르고, 코드는 화면이 바뀌었는지만 봄 | `direct.py` |
| 복구 | 판을 못 찾거나 덮개가 있을 때 모델이 입력 하나로 답함. 성공하면 보관해 재생 | `recovery.py` |
| 루틴 | 모델이 판 밖 화면에서 보낸 입력을 "이 화면이면 이 입력"으로 보관하고, 같은 화면이 다시 서면 코드가 묻지 않고 보냄. 맞는 단계가 없는 화면만 모델에게(§28) | `routine.py`, `agent._by_routine` |
| 끌기 | 집은 것이 그려지는 자리를 재서 놓을 곳을 맞춤 | `carry.py` |
| 화면 | 웹(Playwright), Android(ADB), 움직임 걷어내기 | `environments/`, `frames.py`, `motion.py` |
| 요청·식별 | 말로 한 요청을 목표로 바꾸고, 계열 후보를 골라 첫 수로 확인 | `request.py`, `adaptation.identify` |
| 루프 | 위를 잇는 한 판의 흐름 | `agent.py` |
| 작업 | 요청한 범위만큼 판을 잇고 돌려주기(레벨 N개, 예산 하나, 돌려주기) | `work.py` |
| 화면 종류 | 판, 결과, 지도, 팝업, 튜토리얼, 이야기, 다른 퍼즐, 로딩. 화면을 보는 모델이 붙이고 코드는 그 이름으로 가름. 판 사이에서 같은 화면을 맴도는지 봄 | `scenes.py` |
| 보관 | 사이트(앱)마다, 한 앱에 게임이 여럿이면 요청이 고른 게임마다 폴더 하나: 계열별 판독기·값·복구, 루틴(`routines/`), 모델의 기억(`memory.json`), 모델이 만든 계열(`made.json`) | `adaptation.Store`, `adaptation.keyed` |

목표 계약은 `contracts.GoalSpec`이다. 목표는 `play_until_end`, `reach_value`, `actions`, `levels` 넷이고, `scope`(지금 화면에서 / 새로 띄워서), `stop_conditions`(`lost` 또는 사람의 말), `allowed_meta_actions`(`boosters`, `currency`, `continue`, `retry`)를 쓴다(§25 기록).

## 남은 문제

새 방향과 닿는 것:

- **판 사이 넘기기는 세션 B에서 풀렸고, 같은 길을 다시 묻는 비용은 세션 D의 루틴이 줄였다**(§28 기록): 한 번 모델이 넘긴 화면은 다음부터 코드가 누른다. 진 레벨을 다시 두는 구간은 모델 입력 0번(10~21초)이 됐다. 깬 뒤의 길은 아직 구간마다 모델이 1~4번 낀다: 레벨마다 처음 보는 창(보상, 새 부스터 안내)이 끼어들고, 그 창은 한 번은 모델이 봐야 한다. 깬 뒤의 길 전체가 모델 없이 지나간 구간은 아직 못 봤다.
- **레벨의 끝을 다음 화면으로 미루어 판정하는 때가 있다.** 게임이 결과 화면 없이 지도나 보상 창으로 넘어가면 복구 모델이 "이겼다"를 그 화면에서 추정한다(§25 세션 B 기록). 진 뒤 지도로 넘어가는 게임에서는 틀릴 수 있다. 세션 C3에서 고치지는 못하고, 끝을 어떤 화면에서 말했는지를 부분마다 남기게 했다(`end.inferred`). 원인: 레벨이 어떻게 끝났는지를 말해 주는 것이 모델의 말 하나뿐이다. 코드가 따로 아는 것은 덜 센 목표 수(세지 못한 연쇄가 있어 남은 수가 실제보다 많게 나옴)라서 "졌다"를 뒤집지 못한다. 고치려면 남은 수 칸의 숫자를 읽는 길이 있어야 한다(남은 수 0이고 목표가 남았으면 짐).
- **루틴의 일치 기준은 두 게임의 화면에서 잡은 값이다**(§28 기록). 꿈의 집에서 진 뒤의 카드가 시작 카드 단계에 거리 5.9(기준 6.0)로 맞았다. 웹과 다른 계열에서는 재지 않았다.
- **레벨 안에서 지는 일이 많았다**(세션 D: 꿈의 집 레벨 30·31에서 6번, 로얄 매치 레벨 18에서 1번. 세션 C3: 레벨 33과 23에서 2번씩). 진 레벨마다 끝에서 복구 질문 3~4개가 든다(추가 수 제안 닫기, 끝 판정).
- **3매치 판독은 세션 C3에서 고쳤고 세부가 남았다**(§26 세션 C3 기록). 판독기가 판이 멈춘 뒤에 읽게 되어, 모델이 판을 읽어야 했던 수가 꿈의 집 30% → 약 16%(레벨 3개), 로얄 매치 약 16%. 남은 것: 판독의 28%(꿈의 집)가 상한 6.5초까지 같은 판독이 안 나옴, 판독기가 놓친 뒤 돌아오지 못한 판 하나(실측 뒤 고쳤고 다시 재지 않음), 레벨 첫 판은 여전히 모델이 읽음(목표 때문에 질문 수는 같음).
- **진행 방식을 뼈대 먼저로 바꿨다**(§24, 2026-11-20). 처음 보는 게임, 이름 붙인 작업, 실시간, 지속 세계의 뼈대가 3매치 세부보다 앞이다.
- **실측에서 아직 안 나온 것**: 이름 창 알림(C2-5). 가짜 판 시험만 통과. 하트 0이면 끝내기(C2-4)는 세션 D의 꿈의 집 2판에서 나왔다("다음 하트까지 23분"을 말하고 아무것도 누르지 않고 끝남).
- **후보 중 고르기(§31 L3)의 효과는 숫자가 없다.** 3매치는 레벨마다 난이도가 달라 같은 판에서 견주지 않는다(§26). L3는 3매치 풀이기(`solvers/match3.rank`)에만 있다.
- **§24 뒤의 실측이 Android 3매치 두 게임에만 몰려 있다.** 웹은 한 판도 재지 않았고, 보류 세트는 잰 적이 없다. "웹·Android 범용"의 근거가 이 부분에서 비어 있다(세션 G).
- **3매치 수당 6~20초.** 실시간과는 거리가 멀다.

계열 안에 남은 것(뒤로 미룸, 자세한 것은 보관 파일의 해당 절):

- 3매치: 장애물 종류를 값으로 나누지 않음, 두 겹인 칸, 젤리 판의 잦은 판독 의심(§23). 꿈의 집 레벨 7(잔디 판)에서 거절된 수 뒤로 모델이 읽은 12수가 규칙과 맞지 않았고(수당 40~70초), 레벨 8(사슬)은 세 번 가운데 두 번 수가 떨어져 졌다(§25 세션 B 기록)
- 지뢰찾기: 경량 모델이 숫자를 잘못 읽으면 규칙이 못 잡음(§20)
- 블록 놓기: 웹 튜토리얼 구간 비용, 잘못 놓인 끌기에서 배우기(§19)
- 클론다이크: 자리로 된 판을 코드 생성 없이 읽는 길이 없음(§11)
- 계획만 있고 안 한 것: 웹 DOM 읽기(§15), OCR(§12 B2), 3×3 구역 지우기(§19 K6), 데모 터널(§14 D9)
- 판당 예산 기본값(30만 토큰, 15분)을 다시 정하지 않음(§10)
- 풀이기 실력: 2048(예산 2000에서 2048 도달 66.7%, 공개 최고는 사실상 100%)과 클론다이크(1000판 중 56%가 수 상한에 걸림)가 공개된 최고 방법보다 낮다. 지뢰찾기는 같은 조건 숫자가 없다(§33, 세션 P, 후순위)

## 실측 규칙

- 한 묶음은 3판 이하다. 한 게임에 실측 묶음 하나 넘게 매달리지 않는다. 게임 전용 수정으로 흐르면 멈춘다.
- 계열마다 개발 중 보지 않는 게임을 남긴다. 보류 세트는 스도쿠, 워터 소트, Threes, 마작 솔리테어, 워들류(`sites.json`의 `holdout_*`)이고, 보류 게임에 맞추려고 원인을 보지 않는다.
- 앱을 처음 여는 상태에서 잰다. 사람이 넘긴 구간이 있으면 표에 적고 시작 화면을 `start.png`로 남긴다.
- 표에 모델 이름을 적는다. sol로 된 판과 terra로 된 판은 견주지 않는다.
- 도구: `eval web`, `eval android`, `eval offline`(보관 화면, 비용 0), `eval policies`, `eval checks`, `eval serve`, `pytest`. 판마다 JSON과 `final.png`, 실행마다 `summary.json`.
- 단계가 끝날 때마다 멈춰 승인을 구하지 않는다. 보관 파일 §5의 "사용자 승인 뒤"는 2026-11-14에 바뀌었다.

## 24. 방향: 작업 단위와 실행 방법 (2026-11-17, 사용자와 정함. 계획만)

### 작업

3매치 한 판, 판 사이 화면 넘기기, 일일 보상 받기, 밭 수확을 같은 모양으로 본다. **작업**은 셋을 가진다.

- 시작 조건: 어떤 화면에서 시작할 수 있나
- 실행 방법: 아래 넷 가운데 하나
- 끝 확인: 끝났는지를 화면에서 어떻게 아나

사용자 요청은 "어떤 작업을, 어디까지"가 된다. 지금의 `Agent`는 작업 하나(한 판)를 도는 루프로 남고, 그 위에 작업을 고르고 잇는 한 겹을 둔다.

### 실행 방법을 고르는 기준

정적이냐 동적이냐가 아니라 두 질문으로 가른다. 규칙과 상태를 코드로 적을 수 있나, 한 수를 정하는 데 게임이 시간을 얼마나 주나.

| | 기다려 줌 | 시간이 흐름 |
|---|---|---|
| **규칙을 코드로 적을 수 있음** | 계열 코드(지금의 네 계열) | 코드가 두고 모델은 준비만(테트리스류). §29 |
| **적을 수 없음** | 모델이 직접 판단(판 사이 화면, 스토리, 농장의 경영 판단). §27 | 모델이 느리게 계획하고 코드가 실행(액션, 러너). 맨 뒤 |

| 실행 방법 | 쓰는 곳 | 상태 |
|---|---|---|
| 계열 코드 | 규칙을 아는 계열 | 있음 |
| 모델 직접 | 규칙을 적을 수 없거나 처음 보는 게임 | 있음(`direct.py`), §27에서 보강 |
| 배운 루틴 재생 | 같은 입력이 되풀이되는 작업 | 있음(`routine.py`, 세션 D1). 판 사이 화면에서만 실측, 이름 붙인 작업은 길만 있음(세션 C3) |
| 실시간 코드 루프 | 규칙은 적을 수 있는데 시간이 흐르는 게임 | 없음, §29 |

### 모델 호출

- 코드 풀이기로 묶을 수 없는 게임까지 코드로 한정하지 않는다. 그런 게임은 모델이 판단하고 수를 두며, 호출을 아끼느라 못 두는 일이 없게 한다.
- 대신 하네스(프롬프트, 도구, 기억, 확인)로 모델이 적은 호출로 맞는 방향을 잡게 한다(§27).
- 호출은 처음에 쓰고 갈수록 줄인다: 처음 보는 게임은 모델이 직접 → 성공한 입력 순서는 루틴으로 → 자주 나오는 계열은 키트와 풀이기로.

### 다른 에이전트에서 가져오는 것

코드는 가져오지 않고 개념만 쓴다.

| 출처 | 가져오는 것 | 안 가져오는 까닭 |
|---|---|---|
| Cradle | 목표를 작업으로 나누기, 기억, 결과 점검, 행동을 묶은 기술(§28, §30) | 게임마다 행동 코드와 프롬프트를 사람이 씀. 모델을 기다리는 동안 게임을 멈춤 |
| GamingAgent | 판독·기억 보조가 같은 모델의 성적을 올린다는 결과(§27). 2048과 캔디크러쉬는 비교 기준(§26) | 게임별 설정과 판독 보정이 필요 |

### 순서

§25 → §26 → §27은 지금의 3매치 실측에서 바로 확인되므로 먼저 한다. §27의 첫 적용이 §25의 판 사이 잇기다. §28이 농장형(§30)으로 가는 다리다. §29는 따로 가는 갈래다.

### 진행 방식을 바꿈: 뼈대 먼저 (2026-11-20, 사용자와 정함)

사용자: "지금 속도가 너무 느려. 구현을 어느 정도 뼈대를 잡아놓고, 세부적인 걸 손 보는 식으로." 세션 C, C2, D1, C3이 모두 Android 3매치 두 게임의 판독과 판 사이 세부였고, 그동안 처음 보는 게임(§27 나머지, 보류 세트 실측), 이름 붙인 작업, 실시간(§29), 지속 세계(§30)는 계획만 남았다. C3을 닫은 뒤로는 아래 순서로 간다. 위 표의 D2, E, F, G는 이 순서로 다시 나눈 것이고, P는 그대로 뒤다. 세션 이름과 나눔은 Claude의 제안이라 사용자가 바꿀 수 있다.

- **뼈대 세션의 끝 조건은 "실제 게임 하나에서 끝까지 한 번 돈다"다.** 성공률이나 비율을 올리는 일은 세부 세션으로 넘긴다.
- **뼈대 세션의 실측은 1판이다.** 안 돌면 어디서 막혔는지 한 줄 적고 다음으로 간다. 3판 묶음은 숫자를 내는 세션에서만 쓴다.
- 한 게임의 원인을 파기 전에 "뼈대인가 세부인가"를 묻고, 세부면 맨 아래 줄로 넘긴다.
- 기록은 표 하나와 몇 줄로 줄인다. 전체 pytest는 세션에 한 번.

| 세션 | 범위 | 끝 조건 |
|---|---|---|
| U1 | **처음 보는 게임의 기준선.** 보류 세트(`sites.json`의 `holdout_*`)와 웹에서 계열이 없는 게임을 지금 코드로 1판씩(직접 두기, 만든 계열). 고치지 않음. 앞의 G에서 보류 세트·웹 부분 | 게임마다 한 줄: 진행됐나, 어디까지 갔나, 어디서 막혔나, 질문·토큰 |
| U2 | **이름 붙인 작업 한 바퀴.** 실제 게임 하나의 일일 보상(또는 수확)을 요청으로 맡기고, 두 번째 요청은 루틴이 재생. 길은 세션 C3에서 놓음(`task`) | 두 번째 요청이 모델 입력 없이(또는 끝 확인 한 번으로) `task_done` |
| U3 | **실시간 뼈대.** 앞의 E(측정)와 F의 가장 얇은 루프를 한 세션에. 웹의 떨어지는 블록 게임 하나 | 줄 하나를 지움. 못 하면 찍기·입력 속도 숫자와 못 하는 까닭 |
| U4 | **지속 세계 뼈대**(§30). 세계 기억(가진 것, 끝낸 작업, 다시 익는 때) 한 파일과 작업을 고르는 한 겹. U2 위에 얹음 | 농장형 게임 하나에서 "다 익은 것 수확"이 시간을 두고 두 번 됨 |
| 세부 | U1이 보인 약한 곳부터: 앞의 D2(M7 → M2·M3 → M6), 같은 판에서 방법끼리 견주기(G의 나머지), 꿈의 집 10개 연속 다시 재기(§26 a), P(§33), 스토리형 | 세션을 열 때 정함 |

D2를 "급하지 않다"고 한 근거(C2 뒤 판 위 직접 두기 0.4%)는 계열이 있는 3매치에서 잰 숫자라 계열 없는 게임에는 해당하지 않는다. U1이 그 숫자를 낸다.

**그 전의 순서**(기록으로 둠). 순서는 A → B → B2 → C → C2 → D1이다. D는 2026-11-19 세션에서 D1과 D2로 나눴다: 끝 조건에 닿는 것(보관 키, 루틴, M1 묶음, M4 기억)이 D1이고, D2는 급하지 않다(C2 뒤 판 위 직접 두기가 0.4%, M3·M2는 웹 DOM과 함께일 때 쓸모가 큼). C는 B와 B2 뒤여야 한다(코드를 바꾸면 숫자가 새로 시작). B2는 2026-11-18에 끼웠다: B의 실측에서 계열이 레벨의 목표를 모른 채 두어 지는 것이 드러났고, 그대로 재면 그 숫자가 기준선이 된다(§31). E는 다른 세션과 겹치지 않는 때 아무 때나 한다(에뮬레이터는 한 대). §30은 D가 끝난 뒤에 세션을 정한다. C2는 2026-11-18에 끼웠다: C에서 꿈의 집 레벨 21을 계열이 첫 수 전에 놓아 모델 혼자 두다 6번 졌고, 이것이 D(직접 두기와 루틴)의 실측을 가리지 않게 먼저 고친다(§26 세션 C2 계획). C3과 G는 2026-11-19 계획 점검에서 떠 있던 일을 세션으로 묶은 것이다. C3은 3매치를 다시 재기 전에 한다(판독 문제라 D와 겹치지 않음). G는 D 뒤에 한다. Q는 D 앞에 한다(2026-11-19 사용자: D가 루프를 바꾸기 전에 다른 계열의 기준선).

## 26. 성능 입증 (2026-11-18 사용자와 고침: 3매치는 같은 레벨 10번이 아니라 레벨 10개 연속. 세션 C에서 잼, 기록은 이 절 끝)

**왜 바꿨나.** 꿈의 집, 로얄 매치 같은 레벨 진행형 게임은 깨면 다음 레벨로 넘어가 같은 레벨을 다시 둘 수 없다(진 레벨만 다시 된다). 같은 레벨을 10번 재려면 앱 데이터를 지우고 초반부터 다시 지나야 하는데, 초반은 개발 중에 본 레벨이고 판마다 튜토리얼과 판 사이 구간이 길다.

**정한 것**

- **코드를 고정한다.** 커밋 하나를 정하고(세션 C를 시작할 때의 `main`), 묶음들 사이에는 고치지 않는다. 고치면 그 뒤로 새 숫자이고 표를 따로 한다.
- **게임을 초기화하지 않는다**(사용자 지시 2026-11-18). 앱 데이터 지우기(`pm clear`, `--setup`의 `clear`), 다시 설치, 진행 되돌리기를 하지 않는다. 지금 진행된 곳에서 이어서 잰다. 앱을 다시 띄우는 것(`am start`, 요청의 `new_game`)은 진행을 지우지 않으므로 된다.
- **3매치: 처음 보는 레벨 10개 연속.** 게임마다 지금 레벨부터 10개를 잰다. "레벨 3개 깨줘. 지면 다시 해도 돼" 작업을 3~4번으로 나눈다(실측은 한 번에 3판 이하, 중간에 끊겨도 잃는 것이 적다). 나눈 작업 사이에 사람이 손대지 않는다.
- **대상.** 꿈의 집(지금 레벨 15, 추가 수 제안 화면에 멈춰 있음), 로얄 매치(지금 레벨 7). 캔디크러쉬는 넣을지 정하지 않았다.
- **같은 판에서 방법끼리 견주기는 3매치에서 하지 않는다.** 레벨마다 난이도가 달라 견줄 수 없다. 계열 코드, 후보 중 고르기, 직접 두기를 같은 판에서 견주는 것은 다시 시작되는 게임(Android Puzzles, 웹 2048)에서 따로 한다. 2048과 캔디크러쉬는 GamingAgent의 공개 숫자와 조건(시작 상태, 입력 방식, 예산)을 적어 나란히 두되, 조건이 다르면 우열로 쓰지 않는다.

- 판독기는 시험 3수(`TRIAL_MOVES`) 뒤부터 수를 보낸 지 약 1초(꿈의 집), 2.3초(로얄 매치)에 한 장만 찍어 결과로 받았다. 3매치의 규칙은 바뀐 판이면 결과로 받으므로(`assess`) 연쇄 도중의 판이 확인된 수가 됐다.
- 움직임이 한 번 잡히면(`Steady.moving`) 그 뒤 판독마다 5장의 가운데 값 그림을 읽었고(약 3초, 꿈의 집 판독의 절반), 모델이 읽기 전의 기다림(`_rest`)은 건너뛰었다. 잡힌 움직임은 반짝임이 아니라 연쇄 자체였고, 그것이 다음 판독에서 다시 잡혀 이어졌다.
- 못 읽은 화면은 같은 까닭으로 두 장, 1초가 지나면 모델에게 넘겼다(연출이 판을 덮은 동안).

**M7 프롬프트 나누기**(2026-11-18, 세션 C 중 사용자와 정함. 계획만). 지금 직접 두기의 지시는 계열과 상황에 상관없이 `play_direct.md` 하나이고, 달라지는 것은 요청의 게임 이름(`hint`), 모델의 메모, 최근 입력뿐이다. 꿈의 집 레벨 21(세션 C 기록)에서 계열이 판을 놓은 뒤 모델은 계열이 `match3`인 것도, 판독에 있던 겹·퍼지는 잔디·사슬·종이비행기도 받지 못하고 처음 보는 게임처럼 18수를 세 번 두었다.

- **계열 겹**: 계열마다 하나. 새로 쓰지 않고 계열 설명(`match3.json` 등)의 규칙과 값의 뜻을 꺼내 씀(계열마다 설명 하나, §19·§20). 게임 이름은 넣지 않음. 규칙보다 효과가 클 것은 **그 판에서 코드가 이미 아는 사실**(마지막 판독의 격자, 겹, 묶인 조각, 목표의 성질 `cover`·`spread`)을 글로 주는 것이다(M2와 같은 자리). 계열이 없는 게임은 계열 겹이 비고 지금과 같음.
- **상황 겹**: 계열 구분 없이 공통. 지금 `play_direct.md`에 섞인 문단(`onward`, 동의, 제안 거절, 이야기 넘기기)을 상황별로 꺼냄. 계열에 따라 뜻이 달라지는 곳만 계열 겹에서 덧붙임: `board`가 무엇인가(번호 붙은 레벨 / 한 판 전체), 튜토리얼의 강제 수(두 칸 바꾸기 / 조각 끌기), 결과 화면의 뜻(다음 레벨 / 새 게임을 누르지 않고 끝).
- **상황을 언제 아나**: 화면 종류는 지금 모델이 답에 붙이는 값이라 프롬프트를 고를 때는 모른다. 직전 답의 화면 종류와 코드의 신호(계열이 판을 읽는 중이면 `board`, 레벨이 막 끝났으면 다음 레벨 찾기)로 고르고, 모르면 상황 겹 전부를 짧게 넣는다. 상황을 먼저 묻는 질문을 더하지는 않는다.
- **같이 볼 것**: 프롬프트만으로는 탐색이 생기지 않는다. 레벨 21의 모델 판독은 9번 모두 규칙 검사를 통과했으므로, 코드의 판독기가 판을 놓아도 모델이 읽은 격자로 풀이기나 후보 중 고르기(§31 L3)를 이어 쓰는 길이 더 클 수 있다. M7은 그래도 직접 둘 수밖에 없을 때의 질을 올리는 일이다.

스토리형에서 정할 것: 대사 넘기기는 코드가 하고 선택지에서만 모델이 본다. 되돌릴 수 없는 선택은 사용자의 방침("착한 쪽으로")을 받거나 멈추고 돌려준다(R1의 멈춤 조건). 스토리형은 수요가 확인되지 않아 대상 게임을 정하지 않았다.

## 28. 반복 루틴 (세션 D1에서 함, 기록은 이 절 끝)

- 모델이 직접 둬서 끝낸 작업의 입력 순서를, 사이사이의 확인 지점(이 화면이면 다음 입력)과 함께 보관한다.
- 다음에 같은 작업이 오면 코드가 재생한다. 확인 지점이 어긋나면 그 자리부터 모델로 돌아가고, 고친 순서를 다시 보관한다.
- 복구의 보관·재생(`recovery.py`, `recoveries.json`)을 넓힌 것이다. M1과 같은 장치라 함께 설계한다.
- 앞 일: 보관 키를 앱 안의 게임·작업별로(§12 A1·A3).
- 대상: 일일 보상 받기, 수확, 아이템을 얻는 반복 판.

### 세션 D1 기록 (2026-11-19~20. M1·M4와 §28, 보관 키 A1·A3. Fable 5.2)

**D를 둘로 나눔.** 끝 조건("직접 두기로 끝낸 작업 하나가 다음에 코드 재생으로 끝남")에 닿는 것만 이 세션(D1)에서 했다: 보관 키(A1·A3), 루틴(§28), M1의 서로 다른 입력 묶음, M4 기억. M2(화면을 글로)·M3(이름 있는 도구)·M6(모델 나눠 쓰기)·M7(프롬프트 겹)은 직접 두기의 질이고 끝 조건과 떨어져 있어 D2로 넘긴다(§24 표). M3의 "보관한 루틴 부르기"는 필요가 없어졌다: 루틴은 모델이 부르지 않고 코드가 화면을 보고 스스로 보낸다.

**설계: 루틴은 순서가 아니라 "화면 → 입력"의 모음이다.** 판 사이의 길은 레벨마다 조금씩 다르다(끼어드는 보상 창, 제안, 안내). 입력 순서를 통째로 보관하면 한 군데만 어긋나도 전부 버려야 한다. 그래서 단계 하나를 "이 화면이면 이 입력"으로 보관하고, 재생은 지금 화면에 맞는 단계를 찾아 보내는 것으로 했다. 맞는 단계가 없는 화면만 모델에게 가고, 그 답이 새 단계가 된다. "확인 지점이 어긋나면 그 자리부터 모델로, 고친 순서를 다시 보관"이 따로 만든 복구 절차 없이 이 구조에서 나온다.

- 복구의 입력 하나짜리 보관(세션 B의 `passage`)은 루틴으로 바꿨다. 직접 두기가 꺼진 길(`direct=False`)의 `next` 보관은 그대로다.
- 진 레벨을 다시 두는 버튼은 단계로 두지 않으므로 그 화면은 매번 모델이 본다. 대신 "진 레벨을 다시 두었다"는 작업 겹이 알므로, 모델이 `uses`를 달지 않았어도 작업이 `retry` 1로 센다(`work.play`).
- **M1**: 판이 아닌 화면의 `sequence`(6개까지)는 입력마다 화면을 보고, 조금 바뀐 동안만 다음 것을 보낸다. 안 바뀌거나 장면이 바뀌면(30% 넘게) 멈추고 몇 개를 보냈고 왜 멈췄는지 알린다(`repeat`과 같은 고리). 아직 못 본 화면의 입력은 묶음에 넣지 못하게 했다: 본 적 없는 화면을 코드가 누르면 "누르지 않는 것"을 지킬 눈이 없다. 다른 화면으로 넘어가는 묶음은 루틴이 맡는다(그 화면을 모델이 한 번 본 뒤).
- **M4**: 모델의 메모를 `rules`(규칙)·`ways`(판 밖 화면의 길)·`failed`(해 봤는데 안 된 것)·`plan`(지금 계획)으로 나눴다. 준 부분만 바뀌고 안 준 부분은 남는다. `plan` 말고는 게임별로 보관해(`memory.json`) 다음 작업의 모델이 받는다.
- **A1**: 요청 해석이 "앱 안에서 고른 게임"(`within`: 퍼즐 모음의 `mines`)을 따로 읽고, 그 이름으로 보관 폴더를 나눈다(`…+mines`). 앱이나 주소 이름을 되풀이한 것은 버린다(한 게임짜리 앱의 보관이 갈리지 않게). `--game`으로도 준다. 판독기·값·복구·루틴·기억·만든 계열이 모두 이 키를 따른다.
- **A3**: 모델이 만든 계열(`made`)의 설명과 규칙 코드를 `made.json`에 보관한다. 다음 판은 식별·설명·작성 질문 없이 되살리되, 첫 화면이 그 설명으로 읽히고 규칙 모듈이 그 화면에서 검사를 통과할 때만 쓴다. 떨어지면 쓰지 않고 처음부터 찾는다.
- 모델이 받는 것: 코드가 보낸 입력은 기록에 `sent_by: "program"`으로 들어가, 다시 물을 때 모델이 지금 화면에 어떻게 왔는지 안다.

- **판에 닿지 못한 구간의 입력이 단계로 남았다.** 레벨 29 뒤 지도의 레벨 버튼이 "?"(곁들이 퍼즐 카드를 여는 상태)로 바뀌었고, 모델이 그것을 한 번 눌러 순위표가 뜨자 다른 길을 찾다가 에너지를 쓰는 지도 과제를 두 번 누른 뒤 멈췄다. 그 다섯 입력이 모두 단계로 보관됐다. → 단계는 구간이 레벨의 판에 닿을 때까지 시험 중이고, 닿지 못하면 버린다. 2판 앞에서 이 규칙이 지웠을 다섯 단계(n7~n11)를 보관에서 지웠다.
- **지도가 안 맞았다.** 앱을 띄운 뒤의 지도와 레벨을 끝낸 뒤의 지도는 보는 자리가 달라 화면 전체 거리가 21이었다(기준 12). 버튼 둘레의 배경도 같이 움직여 누른 자리(10%)도 9~22였다. → 누른 자리를 6%로 좁히고 가장 비슷한 70% 칸만 견주며(같은 버튼 0~2.3, 같은 자리의 다른 버튼 14 이상), 지도 종류의 단계는 화면 전체 30까지 받는다. 2판 앞에서 남은 단계의 자리 그림을 보관한 PNG로 다시 계산했다.
- **판 위에서 모델이 잠깐 기다린 화면이 "기다릴 화면"으로 남았다**(레벨 29의 판). → 기다리는 시간을 모델이 기다린 시간의 세 배로 묶었다. 뒤의 판들에는 맞지 않았다(거리 13.8~22.8).
- **에너지를 쓰는 입력에 표시가 없었다.** `currency`의 뜻에 에너지·별과 지도·이야기 과제를 적었다. 2·3판에서는 그런 입력이 나오지 않아 효과는 못 봤다.

**끝 조건 판단.** "직접 두기로 끝낸 작업 하나가 다음에 코드 재생으로 끝남"은 **진 레벨을 다시 두는 구간에서 됨**: 꿈의 집 2판에서 모델이 한 번 지난 길(시작 카드 Play, 그리고 레벨 31의 안내 창 닫기)을 그 뒤 다섯 구간이 모델 입력 0번으로 지나 판에 닿았고, 계열이 이어 두었다. **깬 뒤의 길에서는 부분만 됨**: 지도의 레벨 버튼과 시작 카드는 두 게임 모두 코드가 눌렀지만, 깬 뒤의 구간 셋 모두에 모델이 한 번 이상 끼었다(결과 화면을 처음 봄, 새 요소 안내, 새 부스터가 붙은 시작 카드). 묶음 3판을 다 써서 더 재지 않았다. 다음에 같은 게임에서 깬 레벨이 이어지면 저절로 보인다(보관은 `out/adapters`에 남아 있다).

**남긴 것**

- 깬 뒤의 길 전체가 코드만으로 지나가는 것은 못 봤다. 보려면 레벨이 연달아 깨져야 하는데 꿈의 집은 6번 졌다(C3).
- 일치 기준(화면 12·지도 30·자리 6)은 Android 3매치 두 게임에서만 봤다. 웹과 다른 계열은 재지 않았다(세션 G에서 `routines`의 거리 기록을 같이 볼 것). 꿈의 집의 5.9는 기준에 닿아 있다. 값을 더 손대지 않은 까닭: 근거가 한 게임의 한 화면뿐이라 게임에 맞추는 일이 된다.
- 코드가 `opens` 단계 뒤에 계열을 붙이려다 못 붙은 것이 2번(꿈의 집 2판: 안내 창이 판을 덮음, 하트 없음 창)이고 그때마다 모델 판독 질문 1개가 헛들었다. 두 번 잇달아 그러면 표시를 떼게 해 두었다.
- 한 구간에 단계를 한 번만 보내는 규칙 때문에, 창을 닫고 지도로 돌아온 뒤의 레벨 버튼은 모델이 다시 눌렀다(로얄 매치 4부분). 모델이 같은 자리를 누르면 "두 번 보내도 됨"으로 배우는데, 이번에는 90px 떨어진 곳을 눌러 새 단계가 됐다.
- 결과 화면의 단계는 게임마다 둘째 구간에서야 배운다(첫 구간은 앱을 띄운 뒤라 결과 화면이 없음).
- 루틴의 작업은 `next_level`과 `new_game`뿐이다. 일일 보상·수확처럼 요청이 이름 붙이는 작업(§30)은 작업 이름을 요청에서 받는 길만 더하면 같은 모듈로 된다. 꿈의 집의 일일 보상 창은 `next_level` 구간의 한 단계로 보관됐다(같은 창을 다른 때 찍은 것과 화면 거리 2.6. 안의 그림은 달랐다. 날이 바뀐 창과는 견주지 못했다. 커밋 `d3c3cbc`의 글에 "다른 날"이라고 적은 것은 틀렸다).
- M4의 효과, A3의 실측(만든 계열이 있는 게임을 두 번), M1 묶음의 실측은 없다. 세 판에서 모델은 `sequence`를 한 번도 쓰지 않았다.
- 웹은 재지 않았다.

## 29. 실시간 코드 루프 (계획만, 따로 가는 갈래)

- 대상은 떨어지는 블록류(테트리스류)다. 풀이기는 알려진 평가식(구멍, 높이, 울퉁불퉁함)으로 충분하고, 모델은 처음에 판·조각·다음 조각 칸을 찾아 주는 일만 한다.
- 빠진 것은 "보고, 한 수, 확인"이 아닌 루프다. 계속 찍고, 조각이 떨어지는 동안 입력을 보낸다.
- **첫 일은 설계가 아니라 측정이다.** 웹과 Android에서 찍기와 입력이 초당 몇 번 되는지, 입력이 화면에 보이기까지 얼마나 걸리는지 잰다. Android는 입력 명령 하나가 40~80ms였다(§20 X6). 숫자가 낮은 속도 구간도 못 따라가면 Android는 범위에서 빼고 웹만 한다.

## 30. 지속 세계 (계획만, 맨 뒤)

- 농장형처럼 이전 행동과 쌓인 상태가 남는 게임. 더할 것은 세계 기억(가진 자원, 끝낸 작업, 다시 익는 때)과 목표를 작업으로 나누는 계획이다.
- 첫 대상은 시간이 흘러도 손해가 없는 모바일 농장 게임에서 끝이 분명한 작업 하나("다 익은 작물 수확")다. §28의 루틴 위에 얹는다.
- 규칙도 적을 수 없고 시간도 흐르는 게임(액션, 러너)은 이 뒤다. 모델 직접 플레이의 성적이 가장 낮은 영역이다([조사](origin/2026-11-13-game-agent-survey.md)).

## 31. 3매치: 레벨의 뜻은 모델이, 수는 풀이기가 (2026-11-18, 사용자와 정함. L1~L4 세션 B2에서 함, 기록은 이 절 끝)

**드러난 것**(§25 세션 B 실측, `b1-hs-2`의 기록에서 확인). 꿈의 집 레벨 8(21수, 잔디 60칸, 사슬)을 계열이 규칙에 맞는 수로 두고도 졌다.

- 목표가 `{"kind": "other", "target": null, "count": 60}`으로 읽혔고, 풀이기의 점수(`rules/match3.progress`)는 `target`이 없는 목표를 건너뛴다. 21수 내내 목표와 무관하게 골랐다.
- 규칙의 `under`는 지워지는 겹(젤리)만 안다. 잔디는 반대로, 잔디 위 칸을 낀 매치가 나머지 칸으로 잔디를 넓힌다.
- 첫 판독의 잔디는 가운데 3×3 테두리 8칸이고 사슬이 둘레를 막았는데, 코드가 둔 수 대부분은 맨 위 0~2행이었다.
- 같은 레벨에서 모델이 직접 둔 10수는 수마다 "잔디를 넓힌다"를 적었고 그 판은 깼다(`b1-hs-3`, 한 판뿐).
- 따로: 코드가 확인됨으로 센 수가 32, 레벨의 수 제한은 21, 남은 수 칸이 바뀐 것 21번에 안 바뀐 것 11번. 게임이 받지 않은 수를 받은 것으로 판정했는지 남은 수 칸을 놓쳤는지 가르지 못했다(판 상태가 기록에 없음).

**방향.** 게임과 레벨마다 장애물, 효과, 목표가 다르다. 풀이기만으로는 뜻을 모르고, 모델만으로는 느리고(수당 20초) 연쇄를 따지는 일이 탐색보다 못하다. 그래서 나눈다: **판이 어떻게 움직이는지는 풀이기가, 이 레벨이 무엇을 원하는지는 모델이.**

풀이기가 아는 것은 성질의 표뿐이다(이름이 아니라 성질, §22·§23의 원칙 그대로).

| 묻는 것 | 값 |
|---|---|
| 칸을 차지하나, 조각 위에 얹히나, 아래에 깔리나 | 셋 중 하나 |
| 옮겨지나, 떨어지나, 색으로 줄이 맞나 | 예/아니오 |
| 무엇에 깎이나 | 그 칸의 매치, 옆의 매치, 특수 조각만 |
| 몇 번 맞아야 없어지나 | 숫자 |
| 퍼지나 | 매치로 넓어짐, 가만두면 번짐 |
| 목표 | N개 모으기, 다 없애기, 아래로 내리기, 겹을 N칸까지 넓히기 |

| # | 할 일 | 닿는 곳 |
|---|---|---|
| L1 | **레벨을 열 때 모델이 뜻을 성질로 옮김.** 목표 카드와 새 요소 안내(게임이 스스로 띄우는 설명)를 닫기 전에 읽어 위 표의 값으로. 모르면 null. 판을 읽는 질문에 얹어 호출을 늘리지 않음 | `label_screen.md`, `kits/match3.goals`, `agent._take_goals` |

- 표에 안 들어가는 것(컨베이어, 포털, 시한폭탄, 보스)은 성질로 적으려 들지 않고 L3로 넘긴다.
- L3의 "코드가 계산하고 모델이 고른다"는 규칙을 아는 계열 어디에나 쓸 수 있다. 규칙이 없는 게임에는 못 쓴다(탐색할 것이 없다): 그쪽은 만든 계열(`made.py`)이 규칙을 얻은 뒤의 일이다.
- 재지 않은 것: 성질 표가 실제 레벨의 몇 할을 덮는지, L3가 직접 두기보다 싸고 정확한지. ~~C에서 계열, 후보 중 고르기, 직접 두기를 같은 레벨에서 견줘 숫자로 본다.~~ 2026-11-18에 §26에서 3매치는 같은 판에서 방법을 견주지 않기로 바꿨다(레벨마다 난이도가 다르고 깬 레벨은 다시 못 둠). 그래서 L3의 효과는 지금 숫자가 없고, C·C2의 표에서 고름(`picked`)의 몫만 보인다(§26 "남은 것" c).
- 게임 전용으로 흐르는지의 기준: 성질 하나를 더할 때 그 성질이 두 게임 이상에서 나오는지 본다(겹 넓히기는 꿈의 집과 로얄 매치). 한 게임뿐이면 넣지 않고 L3에 맡긴다.

- **끝난 판이나 이미 목표에 닿은 판을 첫 화면에서 받아 수 0으로 끝냄.** 첫 Android 묶음에서 2048은 11-17의 판(1024 타일이 있는 채 진행 중)이, Mines는 끝난 판의 "COMPLETED" 창이 떠 있었다. 요청 범위가 `new_game`인데도 각각 `goal_reached`(reach_value, 0수)와 `goal_reached`(won, 0수, 요약 "The Mines game is completed")로 돌려줬다(`out/android/q-2048-1`, `q-mines-1`). 사람이 "Mines 끝까지"라고 했을 때 이미 끝난 판을 보고 이겼다고 답하는 것은 틀린 요약이다. 앞의 기준선은 앱 데이터를 지운 뒤라 드러나지 않았다. 정할 것: 끝난 판(결과 창에 새 게임 버튼)이면 새 판을 여는가, 진행 중인데 이미 목표에 닿은 판이면 새 게임이 "진행 중인 판을 버리는 새 게임"(누르지 않는 것)이므로 멈추고 그렇게 말하는가. 재측정은 판 시작 전에 앱 안의 새 게임 버튼을 사람 대신 눌러서 했다(2048 ↻ → RESET, Mines New game. 앱 데이터는 지우지 않음).
- **기기 세션.** 2026-11-17에 열린 다른 스레드의 기기 세션이 남아 에뮬레이터를 잡고 있었다. 사용자 지시로 닫음.

끝 조건: 여섯 판의 표가 나왔고 회귀는 없다. 위의 첫 화면 문제는 루프의 회귀가 아니라 기준선이 가리던 경우다.

### Q 이어서: 첫 화면의 판이 이번 작업의 것이 아닐 때 (2026-11-19, 사용자: 진행 중인데 목표에 닿은 판은 "멈추고 알림")

| 한 것 | 닿은 곳 |
|---|---|
| **새로 띄워서 하는 작업은 첫 화면의 판을 제 것으로 치지 않음**(`anew`): 범위가 `new_game`이고 레벨 작업이 아니며 이번 작업이 한 수도 두지 않았을 때 | `work.play`, `agent.Agent.anew`·`_before_own` |

| 끝난 판: 계열이 읽은 끝난 판은 복구 이유 `new_game`으로, 못 읽은 화면은 맥락의 `anew`로 모델에게 "요청 전에 끝난 판이니 같은 종류의 새 판을 열어라"를 알림. 계열 이름이 있으면 새 판이 열린 뒤 계열이 다시 붙음(`resumable`) | `agent._unstick`·`_begin`, `recovery.NEW_GAME`, 두 프롬프트 |

| 끝난 판에서 배운 새 게임 입력은 같은 처지(`anew`)에서만 다시 보냄. 시험에서 그 입력이 작업 자신의 판이 끝난 뒤에도 재생되어 새 판을 계속 연 것을 보고 고침 | `recovery._replay`·`succeeded` |

- "이어서"(`current_game`, `--resume`)와 레벨 작업은 그대로다.
- 시험: `tests/test_anew.py` 3개(진행 중인 1024 판은 멈추고 알림, 끝난 판은 새 판을 열어 끝까지 둠, 새 판을 못 열면 이겼다고 하지 않음). 새 판 시험은 재생을 고치기 전 코드에서 새 판이 네 번 열려 실패함을 확인. 전체 593개 통과.
- 실측(Puzzles Mines, terra): `q-mines-4`(`--package`, 앱을 다시 띄우지 않음, 첫 화면은 앞 판의 "COMPLETED!" 창) → 복구 `new_game`으로 모델이 New game을 한 번 누름 → 판독기가 19수(모두 확인)로 이김, 13.1초, 질문 1 / 입력 4,638. 같은 화면에서 고치기 전에는 수 0으로 "이김"(`q-mines-1`). `q-mines-3`(`--ask`, 앱을 다시 띄움)은 앱이 스스로 새 판을 열어 이 경우를 재현하지 못함.

## 33. 계열 풀이기의 실력 (2026-11-19, 사용자와 정함. 계획만, 세션 P, 후순위)

**왜.** 계열 코드는 "규칙을 아는 게임에서 가장 강한 방법"이어야 한다(§24). 2026-11-19에 계열마다 공개된 최고 방법을 조사하고 지금 풀이기를 시뮬레이션(`eval policies`: 규칙 모델 안의 씨앗 판, 화면·모델·입력 없음, 비용 0)으로 쟀다. 지뢰찾기·3매치는 공개된 강한 방법과 같은 갈래이고, 2048과 클론다이크는 뒤처진다.

| 계열 | 공개된 최고(입증 정도) | 지금 풀이기(시뮬레이션, 2026-11-19) | 판단 |
|---|---|---|---|
| 지뢰찾기 | 제약 추론 + 정확한 확률 + 동점 때 진행 기준 + 끝판 전부 따지기(JSMinesweeper). 1000만 판에 9×9/10 91.7%, 16×16/40 78.4%, 30×16/99 41.0%. 최적은 증명 안 됨, 사실상 기준선 | `solver` 9×9/10 **95.5%**(1000판, 수당 1.1ms) | 같은 갈래. 우리 판은 첫 칸과 둘레에 지뢰가 없어 더 쉬움 → 같은 조건 숫자가 없음(P1) |
| 2048 | n-tuple 망(TD 학습) + expectimax: 32768 도달 72%, 평균 62.5만 점(2021). 학습 없는 손 평가식 + expectimax도 32768 36%, 2048은 사실상 100% | `expectimax` 예산 2000: 2048 도달 **66.7%**, 1024 93.3%, 평균 3.0만 점(30판, 수당 42ms) | **가장 뒤처짐.** 평가식과 탐색 효율(P2) |
| 클론다이크 | 숨은 카드 있는 실제 규칙: 표본 기반 계획(UCT, hindsight optimization)이 35% 넘게 이김(Bjarnason 외, ICAPS 2009, 최적 정책의 하한). 모든 카드를 보면 약 82%가 풀림(Solvitaire). 사람 Draw 1 30~40% | `greedy` Draw 1 **40.2%**(1000판). **56%의 판이 3000수 상한에 걸림** | 맴돎을 막는 것부터(P3). 논문과 규칙(뽑는 장 수, 덱 다시 돌리기)이 같은지 확인 안 함 |
| 블록 놓기 | 입증된 최고 없음(논문 없음, 상용 솔버·블로그만). "탐욕보다 트레이 끝까지 내다봄"만 공통 | `search` 예산 1000: 평균 7,145점(30판, 2026-11-13 리포트) | 견줄 기준 없음(P5) |
| 3매치 | 입증된 최고 없음. MCTS는 강하지만 느림(King), 목표 진척을 가장 무겁게 둔 탐욕이 DQN보다 나음(Napolitano 2020). [3매치 조사](reports/2026-11-17-match3-agents-survey.md) | 목표 가중 탐욕 + 한 수 더 봄(`_ahead`) | 같은 갈래. 떨어질 조각을 표본으로 채워 더 볼 여지(P6) |

숫자는 서로 다른 규칙과 판 수에서 나왔다. 공개 숫자와 우리 숫자를 나란히 적은 것은 방향을 보려는 것이고, 같은 조건 비교는 P1 뒤다.

**정한 것**

- 풀이기는 지금처럼 순수하게 둔다(표준 라이브러리, JSON 입출력, IO·시계 없음, 난수는 씨앗 있는 것만). 규칙 모델과 함께 옮겨지는 코드다.
- 고칠 때마다 `eval policies`로 같은 씨앗에서 견준다(`vs_baseline`). 표에 수당 시간을 같이 적는다. 기본 `--compute`에서 수당 시간이 그 계열 실측 수당 시간의 10%를 넘으면 기본 예산을 낮춘다.
- 학습한 가중치(2048 n-tuple 등)는 들이지 않는다. 손 평가식과 탐색으로 끝 조건이 안 될 때 다시 정한다.
- 풀이기를 바꾸면 그 계열의 실측 기준선이 새로 시작한다(§26, §32). 바꾼 계열은 다음 실측 세션에서 기준선을 다시 잡는다.

**할 것** (P1 → P2·P3 → 필요하면 P4·P5 → P6)

| | 할 것 | 끝 조건 |
|---|---|---|
| P1 | 재는 길: `eval policies`에 규칙 값 넘기기(판 크기, 지뢰 수, 클론다이크 뽑는 장 수 등)와 지뢰찾기 첫 수 보장 방식(첫 칸만 / 첫 칸과 둘레). 3매치 시뮬레이션이 판당 약 78초(정책·예산 전부, 일꾼 1)라 느린 곳을 찾아 줄임 | 지뢰찾기 9×9/10, 16×16/40, 30×16/99를 첫 칸만 안전으로 각 1만 판, JSMinesweeper 숫자와 나란히. Bjarnason 외의 클론다이크 규칙을 확인해 같은 조건 숫자 |
| P2 | 2048: 평가식을 공개된 손 평가식(빈 칸, 단조성, 매끄러움, 합칠 수 있는 짝)으로, 같은 판 표 기억과 확률이 작은 갈래 자르기 | 100판에서 같은 수당 시간에 2048 도달 95% 이상(지금 66.7%) |
| P3 | 클론다이크: (a) 맴돎 막기(본 상태 기억, 바로 되돌리는 수 안 둠). (b) 숨은 카드를 표본으로 채워 굴려 보는 계획(hindsight optimization 류, 씨앗 있는 난수) | (a) 수 상한에 걸린 판 56% → 1% 이하. (b) 1000판 승률이 `greedy`보다 오름, 같은 조건의 논문 숫자(35% 넘음)와 나란히 |
| P4 | 지뢰찾기: P1 숫자가 JSMinesweeper보다 2%p 넘게 낮을 때만. 동점일 때 진행 기준(열면 새로 확실해지는 칸이 많은 칸), 남은 칸이 적을 때 끝판 전부 따지기 | 같은 조건 승률 차이 2%p 안 |
| P5 | 블록 놓기: 평가식에 "다음 트레이 조각이 들어갈 자리 수", 다음 트레이를 표본으로 뽑아 평균 | 같은 씨앗 30판 평균 점수가 지금 `search`보다 오름 |
| P6 | 3매치: 떨어질 조각을 표본으로 채워 2~3수 앞을 봄. 모든 후보에 같은 표본을 씀(실제 새 조각을 알고 두면 실력이 부풀려짐, §23 조사). C3과 3매치 재측정 뒤 | 같은 씨앗에서 목표 달성률이 `greedy`보다 오름 |

**우선순위(2026-11-19 판단).** 후순위다. 세션 G 뒤에 한다.

- 실측에서 지는 주된 원인은 풀이기가 아니라 판독과 판 놓침이었다(§26 C·C2, C3).
- 실측 목표가 낮다. 웹·앱 2048은 1024까지이고 지금 풀이기도 시뮬레이션에서 1024를 93% 넘긴다.
- 풀이기를 바꾸면 Q와 C의 기준선이 새로 시작한다.
- 에뮬레이터와 모델 비용이 없어 다른 세션과 겹쳐도 되지만, 실측 세션이 도는 동안 계열 코드를 바꾸면 한 묶음 안에서 코드가 섞인다. 실측 세션이 없는 때 한다.
- 예외: 실측에서 풀이기 탓으로 지는 판이 나오면(예: 클론다이크가 맴돌다 예산을 다 씀) 그 계열 항목만 앞당긴다.
